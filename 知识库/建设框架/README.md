# 面向 LLM／AI Coding 的知识库建设框架

一个 Agent 要修改项目接口，首先需要获得当前接口契约；随后需要理解设计理由和项目约定；如果还要执行变更，就必须满足权限、验证和审计要求。知识库建设因此可以从三个方面展开：**让知识可获取，让知识可积累，让知识与行动可治理。**

本文基于用户提供的三层动机，自主整理建设重点、交付物与验收建议。它是规划框架，不是行业标准或已经部署的系统。

## 1. 三层动机与建设目标

| 层次 | 解决的问题 | 典型形态 | 建设目标 |
|---|---|---|---|
| **基础层** | 模型不会自动获得私有资料和最新状态 | RAG＋向量库，也可结合关键词检索、结构化查询和直接读取 | 在任务需要时提供适用、可回查的证据 |
| **进阶层** | 知识需要积累、复用与演进 | LLM Wiki／持续编译 | 将原始资料整理为有来源、可维护的知识资产 |
| **企业层** | 决策和行动需要可追溯、可审计 | 知识图谱＋本体，结合权限、规则与审计机制 | 对齐业务语义，记录决策依据并约束行动 |

三个层次是建设侧重点，**不是必须逐级完成的技术路线**。基础层也需要权限和日志；企业层仍需原始证据与检索。只有存在关系查询和共享语义需求时，才需要评估图谱与本体，不能因“企业级”就默认采用全部技术。

从通用问答走向具体任务执行，知识供给的重要性上升：模型需要知道本项目的规则、当前事实与操作依据。对许多 LLM／AI Coding 应用，知识供给已经成为关键瓶颈；但模型能力、工具可靠性、任务设计和业务验收仍可能限制效果，不能认为知识库能独立解决所有问题。

## 2. 基础层：让模型获得任务所需的知识

**核心问题：这次任务需要什么事实，能否找到正确版本并回查来源？**

### 建设重点

- **确定事实来源**：区分当前代码、接口定义、正式制度、设计方案、历史记录和个人笔记的效力。
- **接入与更新**：定义采集范围、刷新方式、版本标识、删除和失效处理；“最新”必须对应可验证的更新时间或版本。
- **组织与检索**：根据任务选择关键词、向量、元数据过滤、结构化查询或直接读取，并保留来源定位。
- **控制上下文**：只提供与任务相关且用户有权访问的内容，避免把过期材料和无关片段一起喂给模型。
- **表达证据边界**：证据缺失、冲突或不足时，允许说明未知，避免强行生成确定结论。

RAG 是检索增强生成的机制，向量库是可选检索组件。小型代码项目可以先从按路径读取、全文搜索和明确的项目入口开始，不必先部署独立向量数据库。

### 建议交付物与验收

| 建议交付物 | 验收问题 |
|---|---|
| 来源清单、有效性和管理责任 | 同一问题出现多个版本时，能否判断应使用哪个？ |
| 文档／代码接入与更新规则 | 更新、删除和权限变化后，旧内容是否仍会被错误返回？ |
| 检索与证据返回约定 | 能否从答案定位到原文、代码位置及相应版本？ |
| 代表性任务与预期证据集 | 是否找到必要证据，答案是否受这些证据支持？ |

**AI Coding 教学示例**：询问“这个接口现在是否需要鉴权”时，应读取当前路由、鉴权逻辑和接口契约。历史设计文档可解释演变，但不能单独证明当前实现。

## 3. 进阶层：让知识持续积累，而非反复整理

**核心问题：已经核实过的理解，如何被下一次任务复用并在变化后修订？**

LLM Wiki 可以把分散资料整理为主题页、术语页、设计决策与交叉引用。持续编译在这里指随着资料变化反复提取、组织、校验和更新知识，成果仍需要保留来源和适用边界。可参考本库的 [Karpathy LLM Wiki 研究](../案例/Andrej-Karpathy/README.md)；以下建设建议是本文整理，不是作者规定的统一模板。

### 建设重点

- **保留原始资料**：整理后的 Wiki 是派生知识层，不能替代原始事实来源。
- **明确页面契约**：记录主题、结论、证据、适用范围、版本和未决问题；区分事实、推断与建议。
- **建立维护闭环**：资料变化→识别受影响页面→生成修订建议→核验→发布→保存变更记录。
- **处理失效与矛盾**：旧页面过期时应修订、标记或撤销；矛盾需要解释，不能仅被新摘要覆盖。
- **受控回写**：问答结果和任务经验可成为候选知识，经验证和审查后纳入；模型输出不应自动成为可信事实。

### 建议交付物与验收

| 建议交付物 | 验收问题 |
|---|---|
| Wiki 导航、主题页与来源关联 | 同类任务是否能复用已整理的依据，并回到原文核验？ |
| 页面更新、失效与冲突处理规则 | 代码或制度变化后，相关页面是否同步修订或标记失效？ |
| 候选知识与审核记录 | 错误问答是否会被阻止进入正式知识层？ |
| 连续任务评估 | 在相同条件下，复用是否减少重复整理，且未降低正确性？ |

**AI Coding 教学示例**：首次修改鉴权模块后，归档已验证的设计理由与验证步骤。下一次相关任务先读取这些知识，再检查当前代码和版本；发生变化时更新页面，而不是沿用旧结论。

## 4. 企业层：让知识和行动受到业务治理

**核心问题：一个业务判断依据什么，对哪些对象生效，由谁授权，执行后能否回查？**

知识图谱可记录具体实体、关系和证据关联。本体可建立共享概念、关系语义、约束与业务模型；运营型应用还可联系状态、规则和行动。相关边界见 [知识库、知识图谱、知识本体](../知识库知识图谱与本体/README.md)。执行能力由平台和工具实现，并不是本体文件自动产生的能力。

### 建设重点

- **统一语义**：明确对象标识、业务概念、关系含义、状态和规则，解决跨系统同名异义与同义异名。
- **组织证据**：业务事实关联来源、生效时间、版本和管理责任；明确如何处理冲突、撤回与更正。
- **区分规则和判断**：把已批准的规则与模型生成的建议分开；需要确定性校验的条件由相应规则或程序验证。
- **控制行动**：明确身份权限、可操作范围、审批与例外处理，知识可读不代表操作被授权。
- **记录全过程**：保存实际使用的证据版本、规则版本、工具调用、授权和执行结果，支持回查与责任界定。

图上的查询或规则路径可以解释系统使用了哪些关联和规则，**不能证明大模型内部推理过程，也不能自动保证事实真实、决策正确或业务合规**。图谱与本体还必须和权限、日志、规则执行及人工治理结合。

### 建议交付物与验收

| 建议交付物 | 验收问题 |
|---|---|
| 本体／业务语义模型及维护规则 | 不同部门对同一对象和规则是否使用一致定义？ |
| 实体、关系与来源记录 | 能否追溯事实来自何处，在何时有效？ |
| 行动权限与规则校验约定 | 未授权、违反条件或证据不足时是否阻止执行？ |
| 决策、审批、调用与结果日志 | 能否回查一次行动的依据、授权和实际结果？ |

**AI Coding 教学示例**：识别依赖废弃 API 的服务及负责人时，可以组合代码依赖信息和组织关系；替换接口或发布服务前，仍需核对依赖版本、权限、测试与发布规则。

## 5. 如何确定建设顺序

先选择具体任务，再识别主要缺口。以下顺序是实践建议，可按风险与已有资产调整：

1. **选定任务与验收条件**：例如定位当前鉴权规则，明确正确答案、必要证据、访问边界与失败处理。
2. **建立最小证据闭环**：先验证来源、更新、检索和回查是否可靠，同时落实权限与基本日志。
3. **在重复任务中验证积累价值**：只有反复需要跨资料整理时，才扩展 Wiki 和持续维护机制。
4. **按业务需求结构化**：关系查询、共享语义或行动规则成为明确需求时，评估图谱、本体及执行治理。
5. **持续评估与修订**：分别评估检索、回答、知识维护和行动结果，不能只看向量召回率或模型回答流畅度。

## 6. 贯穿三层的建设原则

| 原则 | 必须回答的问题 |
|---|---|
| 任务导向 | 哪些任务需要哪些知识，怎样判断完成？ |
| 来源与时效 | 原始依据是什么，当前是否有效，谁负责维护？ |
| 权限与边界 | 谁可以读取、修改和执行，哪些内容不得跨范围使用？ |
| 知识质量 | 怎样识别矛盾、过期、重复和模型生成的错误？ |
| 反馈与演进 | 错误如何修正，相关派生知识如何同步更新？ |
| 可验证性 | 哪些指标和实际任务证明建设有效？ |

本库当前提供文档、摘要、来源与按需加载入口。本文列出的运行时检索、自动编译、图谱查询和行动治理是建设建议，不表示这些系统已在仓库中部署。
