# DeepSeek 分析整理：知识组织与 AI Coding 交付闭环

来源：[DeepSeek 分享对话](https://chat.deepseek.com/share/zxjlgvihg3osema6h9)。读取日期：2026-10-14。

**核心结论：用稳定的内容分类组织知识，用独立属性说明来源、效力和版本，用受控交付闭环连接需求、实现与运行证据。** 是否需要本体与运行时，应由具体查询、语义和行动需求决定。

本文先梳理分享对话的论点演进，再给出自主分析与设计建议。分享是 AI 生成内容，不作为权威规范。页面包含可见的思考、检索说明和回答；它们可用于了解讨论如何修正观点，不能证明其引用、代码或技术结论已经验证。最后一个问题“source: intent / source: derived 是标准叫法吗”在当前分享中没有回答。

## 1. 分析过程：问题如何逐步收敛

| 用户追问 | 对话的主要推进 | 本文保留的认识 |
|---|---|---|
| 为什么建设知识库？ | 从私有信息、积累、审计三个需求展开 | 三层是建设目标，技术按需组合 |
| 怎样同时服务业务问答与研发？ | 提出业务、架构、工程、运维四类内容 | 共享来源，按任务跨类读取 |
| 每类包含什么？前端放哪里？ | 补内容清单与前端子域 | 按知识职责确定归属 |
| 如何结构化，采用本体模式？ | 引入对象、属性、关系、动作 | 从表达格式转向语义与运行能力 |
| 代码定义和 YAML 有何区别？ | 修正“换语法即升级”的思路 | 定义、校验、执行要分别判断 |
| 与已有业务代码是否重复？ | 转向从现有资产派生知识 | 减少重复维护，但保留意图与决策 |
| 如何保持一致？ | 提出派生、差异检测与流程绑定 | 按可验证范围控制漂移 |
| AI Coding 依赖知识库，如何启动？ | 区分需求先行与实现回流 | 用版本和时间轴组织反馈 |
| 为什么又增加分类？ | 将意图／实现改为属性标注 | 内容分类与知识角色保持独立 |

对话的价值主要在追问带来的修正：起初偏重目录与工具，后来转向来源、生命周期与验证。本文不会把早期回答和后期修正并列当成最终方案，也不照录未经验证的工具安装和代码示例。

## 2. 自主整理：三个维度，回答三种问题

| 维度 | 回答的问题 | 使用方式 |
|---|---|---|
| 建设目标 | 为什么建、需要补齐什么能力？ | 知识可达、持续积累、行动治理 |
| 内容分类 | 这条知识主要描述什么？ | 业务、架构、工程、运维 |
| 属性与生命周期 | 从何而来，是什么效力，何时有效？ | 来源、角色、审核状态、版本、生效范围 |

**三层建设目标与四类内容不能相互替代。** 例如，业务规则既可能被 RAG 检索，也可能编译为 Wiki 或建模为本体。目录里的“架构知识”也不是 TOGAF 四个架构域的替代分类；企业架构内容与研发知识分类之间应另建映射。

一个知识单元尽量拥有明确的主归属和稳定标识，其他入口通过索引、标签和关系引用它。不同权限范围可以提供不同视图；不能为了统一知识而扩大访问权限。

### 2.1 四类内容的整理清单

下表是结合任务需求的自主清单，按项目裁剪，不要求每类都有独立目录或完整文档集合。

| 内容类别 | 应回答的问题 | 可收录的信息 |
|---|---|---|
| 业务 | 用户要完成什么，哪些规则和范围有效？ | 术语、目标、用户旅程、流程与状态、规则与例外、指标口径、验收条件 |
| 架构 | 系统为什么这样划分，变化影响哪里？ | 系统与模块边界、职责、依赖、数据流、设计决策、质量要求、失败模式 |
| 工程 | 如何在项目约定下实现和验证？ | 接口契约、编码约定、开发环境、组件与页面规范、测试策略、构建与检查命令 |
| 运维 | 哪个版本在运行，如何观察、发布和恢复？ | 环境与发布记录、监控口径、运行手册、恢复步骤、运行证据、复盘与改进项 |

分类本身不决定稳定性：已批准制度也会变化，接口契约可能频繁演进，运行手册也可能长期稳定。应逐条标注有效版本与复核条件。

### 2.2 页面、交互与通用组件的归属

| 材料 | 建议主归属 | 需要引用的其他内容 |
|---|---|---|
| 用户目标、业务步骤、资格与例外规则 | 业务 | 页面、业务对象、验收条件 |
| 框架、状态管理、模块划分的设计决定 | 架构 | 工程实现与决策记录 |
| 通用组件契约、设计令牌、用法与反例 | 工程／前端 | 设计依据、组件源码与测试 |
| 页面路由、布局、状态、数据加载与错误处理 | 工程／前端 | 用户任务、接口和权限规则 |
| 加载反馈、键盘操作、空态等交互约定 | 工程／前端 | 用户需求、可访问性要求 |

交互也可能承载业务规则。例如“哪些订单允许申请退款”属于业务；按钮如何呈现和反馈属于工程。前端隐藏按钮不能替代后端授权校验。

## 3. 自主整理：事实来源、知识角色与状态分开标注

分享末尾把 `intent`／`derived` 当作 `source` 的两个取值，但二者没有严格对称：前者表达知识用途或效力，后者表达生成方式。**从批准需求提取的内容既可以表达意图，也可以是派生结果。** 不宜用一个二值字段同时承载这两种含义。

本文将这些名称作为自定义设计标签，不作为行业标准。若要标准化记录来源与派生过程，可以参考 W3C PROV-O 的实体、活动、主体及派生关系；它不等于“intent／derived”的二分分类。[W3C PROV-O](https://www.w3.org/TR/prov-o/)

建议至少区分：

| 属性 | 说明 | 示例取值／记录 |
|---|---|---|
| 主分类 | 知识内容的归属 | 业务、架构、工程、运维 |
| 知识角色 | 目标要求、实现描述还是运行观察？ | intended、implemented、observed |
| 来源引用 | 可定位的原始依据 | 需求记录、契约、代码提交、部署或运行记录 |
| 生成方式 | 如何形成当前知识单元？ | 人工整理、工具提取、LLM 辅助整理 |
| 审核状态 | 是否经过相应审核？ | 草稿、已审核、已取代 |
| 实现与部署状态 | 目标是否已实现并在指定环境生效？ | 待实现、已验证、已合并、已部署，分别记录 |
| 版本与范围 | 什么时间、系统与环境适用？ | 来源版本、生效时间、环境、复核条件 |
| 管理责任与访问 | 谁维护，谁可以使用？ | 负责人、审核者、访问策略引用 |

这些属性是本文设计建议，**不是本仓库 `topic.json` 已支持的新增字段**。当前仓库仍按既有元数据 schema 管理主题。示例属性可先用于正文记录，正式扩展工具前需要另行设计与校验。

意图、实现和观察可以通过同一个规则或功能 ID 关联，但不能互相覆盖：已批准的目标不等于已经实现，已合并的实现不等于已经部署，观测记录也需要标明环境和时间。

## 4. 自主分析：结构化、本体和运行时的边界

“用代码定义本体”是否必要，取决于它增加了什么能力，而不是文件后缀。

| 层面 | 要确定的内容 | 不能据此推导的能力 |
|---|---|---|
| 表达与存储 | Markdown、YAML、JSON 或代码如何承载内容？ | 格式本身不提供可信度、权限或执行能力 |
| 数据契约 | 类型、字段与约束如何校验？ | 结构合格不等于业务语义正确 |
| 语义模型 | 对象、关系、概念与规则怎样共享？ | 拥有实体关系不等于自动获得业务推理 |
| 行动与运行时 | 查询、同步、校验、权限和操作如何实现？ | 动作定义不等于已实现、安全或已授权 |

JSON Schema 提供 JSON 数据结构与约束的描述和校验机制；OWL 2 提供形式语义，供推理工具使用。YAML 是表达载体，Python 类的效力也取决于解释和验证工具。因此不能概括为“Python≈YAML≈OWL，语义完全一样”。[JSON Schema 官方介绍](https://json-schema.org/overview/what-is-jsonschema)；[W3C OWL 2 概述](https://www.w3.org/TR/owl2-overview/)

Palantir 将 Ontology 定位为联系数字资产与现实业务的运营层，同时包含语义元素与行动、函数、安全机制。这个平台模式超出静态类型声明；自建对象定义也不能因此声称拥有 Foundry 的全部能力。[Palantir Ontology 概述](https://www.palantir.com/docs/foundry/ontology/overview/)

它的 Action Type 定义对象、属性和关系的变更及相关行为。具体动作仍需配置规则、参数、权限与实现，不能把任意业务按钮或任意函数直接等同于安全的本体行动。[Palantir Action Types](https://www.palantir.com/docs/foundry/action-types/overview/)

### 4.1 何时值得增加本体

以下是本文的选型建议：

- 若主要任务是定位代码、读取契约与理解少量决策，先完善索引、来源和验证机制。
- 若反复需要跨系统对象对齐、关系查询、影响分析或统一业务语义，评估显式语义模型与图查询。
- 若还要操作业务对象，另行设计执行工具、规则、权限、审计与失败处理。

不要在知识层手工重写所有代码结构。适合提取的实现信息可以派生；业务含义、批准要求和历史理由需要各自的原始依据。Markdown 可保留解释与上下文，结构化资产承担查询与校验，二者可以并存。

## 5. 自主设计：避免循环依赖的交付闭环

**教学／设计示例**：将某产品的退款期限从 7 天调整为 14 天。数字与规则仅用于说明，未表示法律要求或任何企业政策。

| 步骤 | 输入与工作 | 产生的知识／证据 |
|---|---|---|
| 1. 定义变更 | 核实目标、范围、例外、生效安排和批准依据 | 目标规则与验收条件，标记待实现 |
| 2. 核实当前状态 | 读取现行规则、契约、相关代码、测试及部署版本 | 带版本的现状与影响范围 |
| 3. 设计与实现 | Agent 在授权任务范围内提出或执行变更 | 候选代码、决策和测试变更 |
| 4. 验证与审核 | 检查边界、异常、权限和兼容性，审核设计与实现 | 验证结果及接受／拒绝记录 |
| 5. 发布与确认 | 区分合并、部署、运行验证三个事件 | 各环境实际生效的版本和证据 |
| 6. 更新派生知识 | 基于被接受的来源提取、修订和发布知识 | 来源版本、更新记录、失效页面处理 |

```mermaid
flowchart LR
    R[批准需求与设计] --> K[任务知识：目标与边界]
    C[当前代码、契约与运行证据] --> K
    K --> A[AI Coding：候选变更]
    A --> V[测试、审核与授权检查]
    V --> M[接受的实现]
    M --> D[部署与运行验证]
    M --> U[受控提取与知识更新]
    D --> U
    U --> K
```

图是本文的闭环示意。它依赖新的需求与明确任务推进，不是让 Agent 因任意文档变化无限执行。

启动新功能时，知识来自批准的需求、设计与已有资产，不必等待新代码存在。修改已有功能时，当前代码与运行证据也必须被核实。知识库可以帮助导航，但不能替代必要的代码阅读与任务验证。

### 5.1 一致性要分清验证范围

| 校验对象 | 可采用的机制 | 能证明什么／不能证明什么 |
|---|---|---|
| 派生文件与指定来源 | 固定来源版本、提取工具版本、确定性生成与差异检查 | 可验证派生结果同步；不能证明原始实现正确 |
| 契约与实现 | 契约测试、集成测试、兼容性检查 | 可验证覆盖范围内的一致性；不能只靠 `$ref` 推断业务关系 |
| 实现与批准要求 | 显式验收用例、规则测试和人工审查 | 可验证明确且覆盖到的要求；不能仅用 LLM 解析两段文本证明全部语义等价 |
| 实现与部署 | 构建、发布、配置与运行证据关联 | 可确认特定环境版本；合并记录本身不足以证明上线 |
| 意图、理由与知识解释 | 来源核对、变更流程、责任人复核 | 可管理解释漂移；不能从代码推导全部历史决策 |

文件哈希可用于发现内容变化，不能单独证明语义变更。代码位置宜记录仓库、提交、符号等信息，行号仅作辅助。自动提取只能覆盖可识别的结构；人工维护也不是必然失效，需要明确责任和复核机制。

对于尚未到生效时间的批准变更，目标与当前实现不同可能是正常过渡状态，不应简单判为错误并自动触发改码。应区分预期差距与异常漂移，再按任务授权处理。

## 6. 原分析中需要保留和修正的结论

下表是本文的评估，不代表 DeepSeek 自己已完成这些修正。

| 原分析倾向 | 本文的处理 |
|---|---|
| 四类内容共享知识，按消费者读取 | 保留；增加主归属与权限视图，避免重复副本 |
| Git 管事实，Wiki 管使用 | 保留版本化思路；Git 记录变化，不保证内容正确，来源也不限于 Git |
| 原文错误必须先改原文，不能直接改 Wiki | 区分来源错误与派生错误；摘要提取出错可直接修正派生过程和页面 |
| 代码、YAML、OWL 在语义上等价 | 修正为比较结构、语义和工具行为，不凭格式判断等价 |
| 本体等于系统，Palantir 不存在同步问题 | 不采用绝对结论；映射、更新、版本与执行一致性仍需验证 |
| Schema 和 OpenAPI 足以自动生成所有对象与关系 | 限定为可提取结构；语法引用不必然是业务 Link，语义需确认 |
| 存量系统只有派生这一条路 | 不采用唯一方案论；可组合契约生成、提取、运行观测和人工建模 |
| 代码合并即 implemented | 细分已验证、已合并、已部署与指定环境生效 |
| 三次提问、每月 20 条、覆盖 60% 等数量 | 不作为阈值或效果依据；按任务成本、风险与验证结果制定 |
| intent／derived 是统一标准字段 | 不作为标准采用；拆开知识角色、来源与生成方式 |

## 7. 本仓库的落实方式

本次增加这份分析，并将其链接到建设框架入口；**不迁移现有领域，不创建业务／架构／工程／运维四套空目录，不改变元数据 schema，也未部署提取或运行时系统。**
