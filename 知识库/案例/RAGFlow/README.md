# RAGFlow / InfiniFlow：以文档解析和检索验证为核心

## 提供方及定位

RAGFlow 由 InfiniFlow 维护，公开仓库将其定位为结合 RAG 与 Agent 能力的知识引擎。本案例考察它对复杂文档处理和检索验证的设计，不把项目宣传中的领先、精度或效率表述视为独立测评结论，也不推断 InfiniFlow 内部如何管理知识。

## 官方确认的能力

官方仓库列出文档理解、模板分块、可视化分块检查与人工干预、来源引用，以及不同格式资料的处理能力；可以配置语言模型、嵌入模型，并提供 API。仓库同时介绍本地部署路径。具体解析质量依赖输入文件、解析器和配置，支持格式不等于每种版式都能无损转换。[官方 README](https://github.com/infiniflow/ragflow)

检索测试用于确认预期分块能否召回，提供相似度阈值、向量权重、重排模型、元数据筛选和候选数量等调整项。官方明确：测试页参数不会自动同步到 Chat Assistant 或 Agent；选定配置后仍需在实际使用位置设置。正确证据已召回但回答有误时，应继续检查模型、提示词或应用配置。[检索测试文档](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/retrieval_testing.md)

## 推荐构建流程（研究建议）

1. 制作代表性文档样本集，包含扫描件、跨页表格、多栏排版、图片说明和正文注释。为样本标注必须保留的信息，避免只用干净 TXT 判断可行性。
2. 按文档类型配置解析和分块，保留原文件、页码及来源地址。人工对照原文检查数字、单位、否定词、表格行列和适用条件。
3. 先运行检索测试。为实际问题标注预期文档与证据段落，检查是否召回、排序是否合理，以及元数据过滤是否误排除正确材料。
4. 用固定问题集对比关键词与向量权重、阈值及重排配置；选择结果后，把配置同步到实际问答应用并再测一遍。
5. 将命中证据传给生成环节，要求回答保留来源；对资料不足、版本冲突和无法解析情况设计明确的反馈路径。
6. 固定部署版本、解析器和模型配置，记录一次变更影响哪些文件。上线后检查更新、撤销和删除，并维持解析失败的重试及人工处理队列。

这一流程是研究建议，重点是建立质量门槛，而非增加尽可能多的检索功能。

## 适用场景

适合技术手册、研究报告、操作规程等复杂文档密集场景，以及希望自部署并检查分块与检索过程的技术团队。是否适合本组织，应先看关键资料能否保留完整证据，再看问答体验和资源消耗。

## 限制与治理

原生分块可视化、检索测试和引用帮助定位问题；资料审批、源系统身份映射、细粒度授权、撤销同步及日志保留规则仍需实施设计。本次来源不足以确认跨来源权限自动继承，因此不能默认具备。重排会引入额外推理与延迟，复杂解析也需要资源预算。

仓库 main 与 dev 文档会变化，可能包含新功能或预发布能力，不能将其全部当作某个稳定版本的交付承诺。正式试点要固定版本，再逐项核对。官方主仓库许可为 Apache 2.0，但模型权重、解析组件、服务依赖和导入资料仍需分别核验，不由主项目许可统一授权。[主仓库 LICENSE](https://github.com/infiniflow/ragflow/blob/main/LICENSE)

## 可借鉴点

把解析正确性作为检索质量的前提；把检索测试独立于答案生成；通过“未召回”与“已召回但答错”区分故障位置；显式同步测试与生产配置。对本知识库而言，先保证正文边界和证据结构，再引入自动问答更稳妥。

本条目未部署、未做性能及安全实测；来源及时间边界见[来源与适用边界](来源与适用边界.md)。
