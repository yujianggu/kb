## 定位与原始思路

LLM Wiki 是利用大模型持续整理知识的模式说明，不是已交付的软件或托管平台。它在原始资料与问答之间增加可维护的 Markdown 知识层：新增资料时整理摘要、关系和冲突；查询时复用已整理内容；有价值的结果可再次沉淀。[作者原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

| 作者提出的层次 | 职责 |
|---|---|
| 原始资料 | 保留供核对的来源，模型不修改原件 |
| Wiki | 模型维护主题、实体、综合页面及链接 |
| 组织约定 | 规定目录、页面格式和维护工作流 |

作者区分资料摄取、查询及健康检查，建议维护导航与变更日志。归档回答是可选操作，工具与目录可按需要调整。这些是作者的设计思路，不是实测性能结论。[原始说明的 Architecture 与 Operations 部分](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

## 本库分析：积累的是可复用结论

价值不仅是把片段存入索引，而是保存“已经理解了什么、依据是什么、与哪些知识有关”。反复出现的跨资料问题，可以先利用综合层，再回到原文核验。

代价是维护新的派生资产：遗漏条件的摘要、错误关系或失效结论可能被不断复用。因此，持续整理必须同时考虑来源、变更影响与审查；页面数量增长不代表知识质量提升。

“编译”在这里是知识加工的比喻：将原始资料中的事实、条件与解释组织成适合重复使用的页面。它不是程序编译器，也不保证相同输入必然产生相同结果。结果质量取决于资料、整理约定、模型与复核。

## 推荐组织结构（本库设计）

以下结构用于独立试点，**不是要求本仓库改目录**。已归档的来源快照保留原件；发生变更时新增版本，而不是让模型覆盖旧证据。实时系统仍须查询当前状态。

```text
project-knowledge/
  sources/                 原始材料及版本快照
  wiki/
    overview.md            项目概览与阅读路线
    concepts/              术语与共同含义
    modules/               模块职责、边界与接口
    decisions/             已确认的设计决策
    syntheses/             跨资料分析与比较
  proposals/               待核对的更新建议
  manifests/               来源与受影响页面映射
  checks/                  评测问题与验收记录
  activity.md              摄取、查询归档及维护日志
  maintenance.md           维护约定与权限范围
```

在本仓库应用时，可复用主题 ID、`topic.json` 与 `catalog.json`，而不是再手工维护一份重复总目录。`proposals/` 等名称只是可选设计；是否需要实际建立，应由试点规模决定。

### 页面应承担什么职责

| 页面 | 应回答的问题 | 应避免的问题 |
|---|---|---|
| 来源摘要 | 此资料提出什么，有哪些条件？ | 把一份资料的结论升格为领域共识 |
| 概念页 | 一个术语在当前项目是什么意思？ | 合并含义不同的同名概念 |
| 模块页 | 职责、边界、接口与验证入口在哪里？ | 大段复制代码，形成难同步的副本 |
| 决策页 | 为何选择此方案，否决了什么？ | 用模型推测替代已确认的设计理由 |
| 综合页 | 多份证据支持什么，冲突是什么？ | 隐藏冲突，给出没有依据的统一答案 |

**交叉引用应说明关系**：例如“此接口实现了某决策”“此结论被新版本替代”“此模块依赖另一模块”。只有一批相关链接，尚不能证明它们共享有效依据。

### 建议的页面契约

每个可复用页面至少包含：

| 信息 | 作用 |
|---|---|
| 身份与范围 | 稳定 ID、用途、适用模块／环境 |
| 依据 | 来源 ID、版本、具体位置及必要引用 |
| 结论性质 | 区分来源事实、本库分析、建议与待核实项 |
| 时间与状态 | 何时适用、何时复核、是否过期或被替代 |
| 访问与衍生权限 | 谁可读取页面，来源限制如何约束摘要和综合结论 |
| 关联 | 必需背景、可选相关页、受影响对象 |
| 验证与责任 | 证据核对或测试记录，谁负责确认变更 |

这些是逻辑要求，不直接往本库 `topic.json` 添加未支持字段。来源日期、审核说明等可先保存在正文／来源页；需要扩展机器字段时，另行修改 schema 和解析工具。

综合页引用不同权限的资料时，需要按来源授权和组织政策确定可见范围，必要时拆成分别授权的页面。改写或总结不能使受限知识自动公开；来源撤权后，应复核依赖它的摘要与综合结论。

## 摄取、查询与维护的操作闭环（本库设计）

### 资料摄取：先产生可审查更新

1. **登记输入**：记录材料身份、原始位置、版本与使用权限；确认是原件、转述还是未核实内容。
2. **判断影响**：查现有相关页面，列出哪些结论得到补充、冲突或失效；不默认全库重写。
3. **提取依据**：分离事实、适用条件和作者判断；无法定位的结论进入待核对项。
4. **提出修订**：更新来源摘要、主题页与必要链接，同时列出新增、修改和替代清单。
5. **核对后发布**：检查关键结论与原文对应、页面间一致性和访问边界，再由有权限的人或约定流程确认。
6. **更新导航与记录**：生成索引，记录处理版本、受影响页面及检查结果。

没有通过核对的候选知识，不应与已确认资料无标记混用。外部文档中出现的执行指令也不能自动成为维护权限。

### 查询：区分回答任务与知识更新

先识别任务、版本及允许访问的资料，沿导航选择相关页面；有必要时查原文、当前代码或实时工具。回答保留依据，对冲突和缺口作明确说明。

查询可能形成有价值的综合结果，但不是每次聊天都值得新增页面。满足以下条件再提出归档：问题会重复出现；结论有明确来源与适用范围；现有页面不能更简洁地承载它；敏感与临时信息已经处理。

**归档顺序建议**：更新已有主题 → 新增明确用途的综合页 → 保留为任务记录。模型回答自身不是新的独立事实来源；多次复述同一结论，也不构成多份证据。

### 维护：将结构检查与事实复核分开

| 检查 | 可验证的内容 | 不能自动推出什么 |
|---|---|---|
| 文件与索引检查 | 入口存在、ID 唯一、依赖和索引同步 | 知识结论正确 |
| 来源检查 | 版本、原文定位、引用能否回查 | 原文一定真实或仍适用 |
| 变更检查 | 代码、契约或资料修改后哪些页需复核 | 未命中变更清单的页面全部有效 |
| 语义检查 | 条件遗漏、矛盾、过度概括 | 模型判断可以代替业务裁定 |
| 任务评测 | 对固定任务能否找到并使用正确依据 | 对所有未测试任务同样有效 |

维护时优先处理影响任务正确性的过期与矛盾，再补链接或拆页面。不能用“链接更多”“页面更多”作为质量目标。

## 更新、冲突与过期管理（本库设计）

**建议分开记录两种状态**：证据是否充分，以及内容是否还适用于目标版本。“已核对”页面也可能后来失效。

| 事件 | 推荐处理 |
|---|---|
| 新材料补充旧结论 | 添加依据，检查适用范围是否扩大 |
| 新旧材料互相矛盾 | 保留双方来源、版本和条件，明确待裁定项 |
| 已确认的新版本替代旧版本 | 标注替代关系，默认使用目标版本的现行结论 |
| 代码或接口已变化，页面尚未复核 | 标记时效风险，任务执行前检查当前实现 |
| 来源撤权或需要删除 | 检查摘要、综合页、图索引、向量及缓存中的衍生内容 |

先区分版本差异、场景差异和真实矛盾；不能用“最新文件”“最后写入”直接裁定业务规则。设计意图、实际实现和运行观察也应分别陈述。

页面回退可以借助版本控制，但还要复核它依赖的来源与关联页；恢复文本不意味着它重新适用于当前系统。

## AI Coding 落地建议（本库提出）

1. **限定范围**：先整理一个模块，明确要支持的任务，例如接口修改和故障排查。
2. **建立证据基线**：以当前代码、契约文件、已确认决策为输入，记录提交版本与定位；文档与实现冲突分别说明。
3. **形成主题页**：整理模块职责、接口约束、设计理由、验证方法，保留每条关键结论的来源。
4. **受控更新**：Agent 提出修改，核对来源与影响后再进入可信层；代码改变时检查受影响页面，不直接将会话猜测当作事实。
5. **任务使用**：先读相关摘要，必要时读取代码和原文；实施与测试结果只能证明本次验证范围，不能自动升级为通用规则。
6. **持续维护**：检查失效路径、矛盾、无来源结论及孤立页面；对撤权和删除同时处理整理页、索引与缓存。

**教学示例**：鉴权模块 Wiki 可记录“为何采用该权限模型”、当前契约位置、兼容条件和测试入口。它帮助 Agent 定位资料，但修改接口仍需对照当前代码与测试，不能凭旧摘要直接执行。

完整的两轮任务示例见[AI Coding 项目 Wiki](案例-AI-Coding项目Wiki.md)，其中展示一次接口变化如何触发页面修订，以及下一次任务怎样复用修订结果。

## 人与 Agent 的责任（本库设计）

| 参与者 | 建议责任 |
|---|---|
| 资料／业务负责人 | 确认权威来源、适用范围和业务冲突 |
| Agent | 提取、组织、提出修订、检查链接并给出依据 |
| 工程人员 | 核对代码事实、运行测试、处理接口及工具变化 |
| 维护流程 | 记录确认、发布、撤销、索引与审计结果 |

个人 Wiki 可以采用轻量审核；企业项目应按变更风险设置确认要求。已有明确授权范围内的日常整理可以自动执行，但扩大权限、覆盖权威规则或执行业务动作不能由 Wiki 内容自行授权。

## 与 RAG 的互补关系

| 方式 | 本库建议的角色 |
|---|---|
| 原文检索 | 找到细节和最新证据，验证整理结果 |
| Wiki 整理层 | 复用跨资料理解、设计理由和关联 |
| 工具查询 | 获取实时状态和实际代码结果 |

可以检索 Wiki，也可以同时检索原文。不能据此断言全部 RAG 都从零开始、Wiki 总是更便宜或准确；收益取决于问题重复程度、变化频率及整理质量。

### 结合知乎讨论：高频综合层与受控事实层

本次结合[徐小夕的专栏](https://zhuanlan.zhihu.com/p/2080072318223639832)和[知乎问题中的可读回答](https://www.zhihu.com/question/2024074329273411299)，补充一个实施判断：**将 Wiki 用于可复用理解，将权威字段、显式关系和实时状态交给对应的数据与查询机制，必要时回到原文核验。** 这是本库的分析，不是对社区自报效果的认证。

建议让有版本的高频综合页成为入口，覆盖不足或来源发生变化时补取证据。存在型号、同义表达和关系查询等不同需求时，再评估词法、向量及关系通道；不要求所有任务都启动三路检索。Markdown 页面链接也不能直接代替已验证的业务关系。

针对中文、长任务和多 Agent 维护，新增验收应包含术语与链接正确性、压缩后的交接信息、并发修改冲突及恢复能力。Git 有助于回查，但不自动解决并发写入或提供独立备份。来源和整理规则变化后允许增量重编译，不能把“只编译一次”当作不可修订原则。

评估成本应累计摄取、查询、复核、更新、存储和失败重试；查询频繁而知识稳定时可能受益，更新频繁或整理质量差时未必。社区试验需保持相同语料与题集才可公平比较。详细作者归属、自报数据及分析见[知乎资料对照与工程补充](知乎资料对照与工程补充.md)。

## 常见失效方式及应对（本库分析）

| 失效方式 | 为什么会发生 | 应对建议 |
|---|---|---|
| 摘要正确但遗漏例外 | 压缩时丢失条件，任务只读短页 | 将适用条件与结论一起保留，必要时回查正文 |
| 错误被反复写回 | 模型输出被当作权威证据 | 归档结论必须有独立来源与核对状态 |
| 旧知识盖过新实现 | 版本和影响清单缺失 | 记录来源版本，变更后复核相关页面 |
| 关系越整理越模糊 | 只堆链接，没有说明关联依据 | 为重要关系说明含义、方向和来源 |
| 维护成本失控 | 每次摄取全库重写、重复页面过多 | 小范围增量更新，定期合并重复内容 |
| 审计记录无法复现 | 只留最终答案，未留资料和配置 | 保存读取版本、更新差异及必要验证记录 |

## 最小试点与验收（本库建议）

从一个模块或主题开始，先定义重复发生的任务，再整理代表性资料；不要先覆盖整个代码库。采用相同来源和任务，比较“直接读原文”与“先读 Wiki 再核验”的结果。

| 目标 | 需要观察的证据 |
|---|---|
| 找得到 | 正确资料与页面能否命中，是否漏掉必要条件 |
| 用得对 | 关键结论是否有依据，版本是否匹配 |
| 能更新 | 新接口或规则到来后，受影响页是否被发现并修订 |
| 可控 | 是否发生越权访问或无依据知识回写 |
| 值得维护 | 阅读、整理、复核和索引的总成本是否改善任务 |

同时记录失败案例、响应时间、输入规模和维护投入。不预设数字门槛或普遍收益，依据试点目标制定验收标准。本次文档没有实际运行这些评测。

## 适用边界与本库关系

适合持续研究或需要反复理解项目背景的工作。资料高频变化、事实要求精确或权限复杂时，应先验证更新成本和错误传播。它不是模型参数训练，也不保证记住全部资料；整理任务本身仍可能受到上下文、工具和模型能力限制。

本仓库已有分层阅读、稳定主题 ID 和来源入口，可以借鉴持续整理的思想。生成索引仍由 `scripts/kb.py` 管理，不能因为作者建议维护导航就手工修改 `catalog.json`。本次仅收录方案，不启用自动编译或自动回写。

在本库维护已确认的内容后，执行以下现有检查：

```bash
python3 scripts/kb.py build
python3 scripts/kb.py check
python3 scripts/kb.py resolve knowledge.case.karpathy-llm-wiki --layer examples
```

这些命令验证结构与读取清单，不会替你确认知识正确性、读取正文或建立持续编译系统。

进一步概念见[知识库介绍](../../介绍/README.md)，证据性质见[来源与适用边界](来源与适用边界.md)。
