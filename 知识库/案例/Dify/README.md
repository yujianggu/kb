# Dify / LangGenius：工作流驱动的知识库应用

## 提供方及定位

Dify 由 LangGenius 提供，知识库是其 AI 应用平台的组成部分。这里收录的是公开产品方案，不是该公司的内部知识管理实践，也不据此认定它优于所有竞品。它的参考价值在于把资料处理、检索和生成组织成可配置的应用流程，便于业务人员参与调整。

## 官方确认的能力

知识库可按领域、用途或来源建立多个集合，并选择性接入应用；官方提供直接创建、定制处理流程以及外部知识库 API 接入路径，同时支持文档与分块管理、检索测试和元数据管理。[Knowledge 总览](https://docs.dify.ai/en/cloud/use-dify/knowledge/readme)

Knowledge Retrieval 节点输出包含内容、标题和元数据的分块数组，可传给 LLM。多个知识库的结果可以汇合处理；知识库层决定初始候选，节点层继续重排或缩小结果。节点提供 Top K、分数阈值和重排设置，并可按元数据过滤。加权设置有索引模式条件，不能假定所有知识库都能使用相同配置。Chatflow 可展示知识引用。[检索节点](https://docs.dify.ai/en/cloud/use-dify/nodes/knowledge-retrieval)

## 推荐构建流程（研究建议）

1. 先选一个明确用途，例如产品支持。收集已审批资料，保留原始链接、文档所有者、发布日期、产品版本及保密等级；相互矛盾的材料先整理。
2. 按资料稳定性和访问边界划分知识库。统一元数据命名，把试验资料与正式资料分开；不要把不同部门的数据全装入同一个集合再依赖提示词隔离。
3. 先导入少量代表性文档，人工查看分块是否包含完整条件、表格说明和例外条款。分块损坏时先修输入和处理规则。
4. 建立输入、检索、生成、回答流程，让生成阶段引用检索结果；增加无依据回答策略、超时处理和人工转接。
5. 准备真实问题及应命中的资料，分别检查候选召回、重排和最终回答。一次只改变一个关键参数，并记录知识库层与节点层的配置组合。
6. 发布前测试旧版本问题、无答案问题和越权请求；上线后由资料所有者处理更新，定期复测删除和失效资料是否仍会出现。

这些步骤是针对知识库建设的设计建议，不代表官方已经自动完成全部治理环节。

## 适用场景

适合小范围文档问答、客服辅助、内部操作指引，以及希望快速验证 RAG 产品流程的团队。若已有知识服务，可以研究外部接口接入，避免重复搬运。正式选型仍需用本组织的语言、版式和问题分布验证。

## 限制与治理

原生检索配置、元数据过滤和引用展示有助于控制上下文，但不等于来源系统的访问权限被自动继承。身份认证、授权映射、内容审批、撤销传播、引用可访问性以及日志脱敏，需要实施团队逐项设计和验收。显示引用也不能证明生成结论完全由引用支持。

自托管代码使用附加条件的 Apache 2.0 修改许可，条款涉及多租户运行及前端标识；涉及这些条件时需按许可核实商业授权。不能把它概括为无约束商用。模型、插件和输入资料还应分别核验。[官方 LICENSE](https://github.com/langgenius/dify/blob/main/LICENSE)

## 可借鉴点

把“哪些资料可进入候选集”和“哪些候选进入模型上下文”分成两个配置层；将检索结果作为独立可检查对象；让业务流程和知识集合解耦。本库可借鉴这些设计，而无需先迁移所有正文。

本条目未部署、未做性能及安全实测；来源及时间边界见[来源与适用边界](来源与适用边界.md)。
