# Elastic：Elasticsearch 混合检索与 RAG 基础设施

## 提供方及定位

Elastic 提供 Elasticsearch 搜索基础设施，本条目聚焦其作为知识库检索层的公开方案。它适合把既有搜索系统扩展到 RAG：检索负责给出相关证据，生成应用据此组织答案。本文不把搜索引擎等同于完整知识管理产品，也不代表 Elastic 内部知识库案例。

## 官方确认的能力

官方文档说明混合检索可以在一次请求中组合全文与向量搜索，返回统一排序；推荐路径包括 semantic_text，也允许自行配置向量字段。官方建议采用 RRF 融合排序。[混合检索总览](https://www.elastic.co/docs/solutions/search/hybrid-search)

RRF 根据各检索结果中的名次合并候选，不要求不同检索器的分数处于同一尺度；可以通过 retriever 组合多个子检索器。结果窗口会影响可融合候选及分页范围，官方列出不支持的 scroll、sort、rescore 等组合，实施时应核对当前接口约束。[RRF 参考](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

官方还提供文档级和字段级读取控制机制；角色权限须配置，相关机制有只读使用条件及查询限制。这是索引访问机制，不足以证明外部资料权限已自动同步。[权限文档](https://www.elastic.co/guide/en/elasticsearch/reference/current/document-level-security.html)

## 推荐构建流程（研究建议）

1. 先确定知识问答对象和检索边界。为文档及分块建立稳定 ID，并保留标题、原始地址、版本、时间和访问标签。
2. 建立关键词检索基线，用产品型号、错误码、人名和制度编号等问题测试精确命中。基线可帮助识别后续语义检索是否改善实际需求。
3. 增加语义检索字段或向量处理流程，并保留可重建索引的原始文本和处理记录。模型变化应通过新索引验证，避免无记录覆盖。
4. 比较关键词、向量及混合检索的证据召回和排序。按标注问题集评估候选窗口、重复分块、延迟及调用成本，而非仅比较演示回答的流畅度。
5. 将授权后的候选传给生成应用，保留引用标识与版本。资料不足时返回缺口，避免让模型补造制度或操作步骤。
6. 建立资料变更到索引的更新、删除与重建流程；在权限变更、模型更换或索引升级后重测，确认应用使用的是预期版本与身份。

以上是建设建议，不是 Elastic 已替用户完成的全套架构。

## 适用场景

适合已使用 Elasticsearch、具备搜索工程能力的组织；尤其适合精确术语、编号和自然语言问题并存的检索需求。若目标只是让少量文档快速形成业务问答，仍需比较其工程投入与一体化应用平台的差异。

## 限制与治理

原生搜索和角色机制可作为基础，但采集授权、资料审批、访问标签映射、源系统撤销同步、回答缓存隔离和生成审核需要自行实现或集成。不能仅依赖用户在查询中提交的过滤条件实现授权；检索到的文本与引用链接都应受服务端身份约束。

RRF 排名不代表答案可信度，候选未命中时融合不能补出证据。模型服务、向量索引和集群运维各有成本，本文不提供容量或响应时间承诺。源码许可选项与默认发行包许可不同，功能可用性还受订阅和部署形态影响；正式选型需分别核对，不可统称全部免费或无约束商用。[软件许可 FAQ](https://www.elastic.co/pricing/faq/licensing)

## 可借鉴点

让精确匹配与语义召回各司其职，以融合层形成候选排序；把检索实验与生成实验分开；保存可重建资料及评测集。对本库可先保留按需加载和主题 ID，再设计独立索引服务。

本条目未部署、未做性能及安全实测；来源及时间边界见[来源与适用边界](来源与适用边界.md)。
