# 知识图谱存储方案

知识图谱不一定要放在专用图数据库里。应先确定**知识如何表示、要执行哪些查询、如何更新与追溯**，再选择存储引擎和部署方式。本页为公开资料研究与设计建议，查阅日期：2026-10-13；没有部署或性能实测。

[领域入口](../../README.md) · [知识图谱入口](../README.md) · [知识库、图谱与本体](../../知识库知识图谱与本体/README.md) · [来源与适用边界](来源与适用边界.md)

## 1. 分开选择表示模型、存储引擎和部署方式

| 维度 | 要决定什么 | 举例 |
|---|---|---|
| 表示模型 | 实体、关系、属性和语义如何表达 | RDF、属性图、关系表 |
| 存储引擎 | 如何持久化、索引、查询和事务更新 | RDF 存储、图数据库、关系数据库 |
| 部署方式 | 谁负责运行、备份、高可用和升级 | 本地嵌入、自托管、云托管 |
| 附加能力 | 是否同库管理文档、向量或分析 | 多模型、向量索引、搜索集成 |

“RDF”和“云托管”不是同一层次的备选项；一个云服务可能支持多个图模型，但不代表不同模型的数据可直接互查或无损转换。

## 2. 主要存储路线

下表的适配判断是本库建议，不是性能排名。

| 路线 | 怎样保存 | 代表与依据 | 优先评估的情况 | 主要责任与限制 |
|---|---|---|---|---|
| 文件与内存图 | 文件保存实体／关系，程序构建查询视图 | JSON、CSV、Turtle 等文件；RDF 表示见下文 | 本地原型、离线交换、版本化小范围模型 | 并发、事务、查询及权限需自行实现；文本易审查不等于大规模查询高效 |
| 关系数据库 | 实体表、关系表及证据表，使用 SQL 联接／递归 | [PostgreSQL 递归查询](https://www.postgresql.org/docs/current/queries-with.html) | 已有 SQL 系统，关系查询范围明确 | 深层遍历、循环处理、索引和模型约束需设计；不预设一定慢于图数据库 |
| 属性图数据库 | 节点、带类型的边及其属性 | [Neo4j 属性图](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)、[NebulaGraph 3.8 模型](https://docs.nebula-graph.io/3.8.0/1.introduction/2.data-model/) | 依赖、责任、影响分析及路径查询 | 语义与本体映射需维护；跨产品身份、边约束和类型支持不同 |
| RDF 三元组／四元组存储 | 主语、谓语、宾语；可组织命名图 | [Jena TDB2](https://jena.apache.org/documentation/tdb2/)、[RDF 概念](https://www.w3.org/TR/rdf11-concepts/) | 需要 IRI、RDF／OWL 互操作与 SPARQL 查询 | 数据入库不自动完成 OWL 推理、SHACL 校验或访问治理 |

### RDF 与属性图的取舍

**RDF** 以三元组表达陈述，RDF dataset 可组织默认图与命名图，适合采用标准标识和语义表示。[W3C RDF 1.1](https://www.w3.org/TR/rdf11-concepts/) 图名可用于组织来源或批次，但图名本身并不证明其中每条陈述的出处、时间或真实性。

**属性图** 可在节点和关系上保存属性，例如一条调用关系的代码位置或观察时间。Neo4j 使用此模型。[官方概念](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/) 一个关系若有多个独立证据或不同时间断言，仍需额外建模，不能只用一个来源字段覆盖历史。

RDF 并非只能保存简单关系，属性图也能承载领域模型；关键在于语义、约束、查询和迁移要求，而非将二者分别称为“学术”和“工程”路线。

### 自托管与托管的区别

Jena TDB2 是单机持久 RDF 存储组件，事务支持并发多读、单写；同一存储目录不能由多个 JVM 同时直接打开。多应用或跨机器访问可通过 Fuseki 服务共享，但这不等于分布式存储或多写集群。[TDB2 文档](https://jena.apache.org/documentation/tdb2/)、[事务文档](https://jena.apache.org/documentation/txn/)、[Fuseki 集成](https://jena.apache.org/documentation/tdb2/tdb2_fuseki.html)

Amazon Neptune 支持属性图的 Gremlin／openCypher 查询和 RDF 的 SPARQL 查询；这说明同一产品支持不同路线，不意味着 RDF 与属性图自动共享同一语义或可以任意跨模型查询。[Neptune 查询文档](https://docs.aws.amazon.com/neptune/latest/userguide/access-graph-queries.html)

托管减少部分基础设施工作；数据模型、来源质量、权限、更新与迁移仍由实施团队验收。套餐、区域、许可和接口限制需按目标版本重新核验。

### 多模型数据库如何理解

多模型描述同一产品管理多种数据形式的能力，而非独立的图表示标准。ArangoDB 3.12 将图节点与边保存为 JSON 文档，分别位于文档集合和边集合；边使用 `_from`、`_to` 指向节点。[数据结构](https://docs.arango.ai/arangodb/3.12/concepts/data-structure/)

本库建议在文档属性与图关系需要共同查询时将其纳入候选，同时检查查询、事务和一致性接口。该版本命名图的一致性保障依赖相应接口，直接修改底层文档不能假定取得同样保障。[图模型与接口边界](https://docs.arango.ai/arangodb/3.12/graphs/)

## 3. 图谱之外还需要保存什么

以下为本库设计建议。不要将全部知识压成节点和边后丢弃原始依据。

| 资产 | 建议保存的位置或形式 | 必须能关联的信息 |
|---|---|---|
| 原始资料与代码 | Git、文档系统或对象存储 | 原文位置、提交／文件版本、访问范围 |
| 本体与模型定义 | 版本化模型文件／模型注册记录 | 对象与关系含义、约束、模型版本 |
| 实体和关联事实 | 图存储或关系表 | 稳定身份、事实状态、适用范围 |
| 断言与证据 | 显式断言对象或证据记录 | 来源、位置、有效时间、入库时间、审查状态 |
| 词法／向量索引 | 同库能力或独立索引服务 | 文档／片段 ID、索引版本、权限标签 |
| 操作与变更记录 | 审计记录、变更日志 | 谁在何时改变了什么，以及验证结果 |

这些是逻辑职责，不要求各用一套物理数据库。向量索引保存相似度检索所需表示，不能单独替代显式依赖关系；图查询也不能替代完整原文检索。

## 4. 需要来源与版本的最小逻辑模型（教学示例）

以“服务 A 调用接口 B”为例，建议区分：

```text
实体：Service-A、API-B、Team-C
关系：Service-A 调用 API-B；Team-C 负责 Service-A
断言：Assertion-001 声明上述调用关系
证据：某代码文件 + 行／符号位置 + Git 提交
治理：有效时间、记录时间、模型版本、确认状态、访问范围
```

这是本库提出的逻辑示例，不是任何数据库的可直接导入模式。使用属性图时，可以把断言建成独立节点；使用 RDF 时，可以采用显式陈述／断言资源组织证据；使用关系库时，可以建立关系记录和证据表。实现应根据实际查询和更新要求选择。

同一关系可以有多条证据。模型抽取分数不应冒充事实正确概率；候选关系与审核后的事实应可区分。区分“事实何时有效”和“系统何时记录”，有助于解释历史决策。

## 5. 更新、删除与安全

以下不是数据库默认保证，需要端到端验证：

1. **稳定身份**：避免把同名对象合并，明确跨仓库、环境和版本的身份范围。
2. **幂等入库**：按源版本和断言身份识别重复，失败可重试，不重复增加关系。
3. **变更与冲突**：保留新旧依据及替代关系；不得仅用“最后写入”判定哪条事实有效。
4. **撤销与删除**：撤销一条证据不一定否定有其他依据的关系；检查图、索引、缓存和备份的处理规则。
5. **访问控制**：按授权限定遍历与输出范围，关系和路径也可能泄露受限对象；模型生成查询需受约束。
6. **备份与恢复**：明确可恢复的数据、模型及索引版本，实际验证恢复流程。

数据校验、形式化推理和业务动作是独立能力。存入图数据库不等于运行本体推理，更不意味着 Agent 获得修改业务数据的权限。

## 6. 按场景选择与验证

| 场景 | 建议先评估 | 验证重点 |
|---|---|---|
| 当前文档库增加少量交叉关系 | 版本化文件或现有关系库 | 关系是否真的改善任务，维护是否可控 |
| AI Coding 调用与责任影响分析 | 属性图库与关系库对比 | 深度／扇出、增量更新、代码版本和路径来源 |
| RDF／OWL 数据交换与语义集成 | RDF 存储及相关校验／推理组件 | 标识、模式映射、SPARQL、语义保真 |
| 需要降低基础设施运维 | 满足模型与区域要求的托管服务 | 成本、备份、权限、导出及服务限制 |

用代表性查询比较同等数据与索引条件：精确实体查找、依赖遍历、负责人联接、带权限的查询、更新与撤销、证据回查及恢复。记录数据量、关系分布、遍历深度、并发和延迟；不根据产品类别假定性能。

**对本仓库的建议**：继续保留 Markdown、元数据和 Git 版本作为可审查资料。需要图谱时，先形成实体、关系、断言、来源及模型的明确契约，再以真实任务验证存储候选。图数据库与索引可作为派生资产，但经人工确认的关系和无法重建的审查记录必须有自己的持久化与备份策略。本次仅新增方案文档，没有安装数据库或创建外部资源。
