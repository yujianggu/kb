# PDCA 循环：案例

> 基于通用知识整理，尚未与视频内容核对。真实案例与假设练习分别标明；假设中的数据仅用于解释过程。
> 内容类型：通用知识版


## 真实案例：拉美医院用小步试验缩短首剂用药等待（2019—2023 年）

### 背景与已发生的结果

IHI 与 St. Jude Global 自 2019 年合作推动儿科肿瘤发热患者的“黄金一小时”改进。首轮 23 家墨西哥医院在 18 个月内，将规定时间内获得首剂抗生素的患者比例由平均 40% 提高至 78%。第二轮扩展到 85 家医院；团队围绕供应、识别、流程和协作测试改进，提交数据并在共同学习会议中修正方案。[IHI 官方项目案例](https://www.ihi.org/partner/consulting/case-studies/golden-hour-collaboratives-minutes-save-lives)

### 具体行动：先在本地测试，再交换数据和经验

项目采用共同改进框架和跨医院学习安排，行动期间用 PDSA 测试想法并提交数据。第二轮把改进点组织到供应、数据学习、及时识别、流程可靠性和团队协作等方面。本文没有取得每家医院的逐轮试验表，因此不编造某院“先移动药柜、再缩短几分钟”的过程。[IHI 项目方法](https://www.ihi.org/partner/consulting/case-studies/golden-hour-collaboratives-minutes-save-lives)

这也说明，循环需要一个合理的改进假设。计划不是抽象地“提高效率”，而是猜测某个流程变化会影响哪段等待；实施后观察是否如预期，并记录其他负担。各地条件不同，共享学习不等于无条件照搬同一方案。

### 结果口径：保留基线、目标人群和轮次

40% 到 78% 描述首轮参与医院的报告结果，不能把它与第二轮汇总数字混在一起。原项目为多措施协作改进，未提供一个仅有循环方法差异的随机对照。阅读时可确认改善发生以及采用的流程，但对单项措施贡献仍需保留不确定。应用到普通业务，最好同时保留逐期数据，防止只比较两个漂亮的端点。

### 与模型的对应（本库分析）

原项目明确使用 PDSA，即 Plan、Do、Study、Act，和 PDCA 属于相关迭代改进方法，但名称与强调点不完全相同。本库用它帮助理解计划、实施、检查学习、调整的循环，不把 PDSA 偷换成原机构自称 PDCA，也不把临床方案写成通用个人医疗建议。

### 可借鉴步骤

对自己的非医疗流程，先定义一次交付的起点、终点和等待时间，收集基线；挑一个可控瓶颈做小范围改变，预先写下预期及观察指标。实施后同时看时间、错误和额外负担，再决定保留、修改或撤回。下一轮从本轮记录继续，避免每次都重新凭印象讨论。

每轮结束留下的应是可继承的记录：当时条件、改变内容、观察结果和下一步。另一个同事应能看懂为何保留或放弃某项措施，这比填满四个阶段的表格更重要。

### 填写示例：减少资料申请中的重复追问

以下是本库假设的非医疗流程，不是医院真实的改进措施。

| 阶段 | 一轮试验应留下什么 |
| --- | --- |
| Plan | 认为缺少进度说明导致追问；限定一种申请类型 |
| Do | 小范围增加进度通知，记录哪些申请确实收到 |
| Check／Study | 看追问次数、总解决时间及通知引发的新问题 |
| Act | 依据观察保留、修改或撤回，并写明下一轮条件 |

试行前明确一次申请从何时算开始、何时算解决，“询问进度”与“补充材料”也要分开。否则通知让用户更早发现缺件，咨询数量可能上升，但流程实际上更顺畅；若只奖励咨询下降，就会误判。

第一次可以只验证通知是否在正确时点触发，不急着证明总体效率。若投递经常失败，就先解决实施问题；不能把未收到通知的人也算作完整接受了干预。第二轮再看问题是否减少，同时观察是否给工作人员增加手动维护成本。

出现好结果后，检查是否恰逢申请更简单或人员增加；若条件改变，就延长观察或分组比较。证据不足的结论可以是“值得继续测试”，不必强行选成功或失败。扩大范围时还需确认新类型是否具有相同等待原因，避免把局部有效的通知复制到所有流程，造成新的消息负担。

### 适用限制

成果来自多机构培训、临床知识、协作和流程变化的组合，不能全部归因于一个循环缩写，也不能由前后对比单独建立严格因果。真实借鉴是让改进成为连续可检查的试验，并有能力失败后调整；如果没有数据口径和实施记录，把会议命名为 PDCA 并不会产生同样结果。

## 假设练习

> 以下保留原有假设练习，供迁移和反例对照；不属于上述真实事件。

### 生活学习：减少复习后的遗忘

**场景：** 小周每天重读单词半小时，但第二天默写表现不稳定，想试试“先回忆，再查看答案”。

**分析：** “感觉更熟”不是记住的直接证据。需要固定次日测试方式，并记录复习时间、词表难度等影响因素。

**行动：** P：记录一周现状，再用一周试行新方法，观察次日回忆正确率与耗时。D：每天保留测试记录，标注漏做和异常。C：假设正确率有所上升，但第二周词表更简单，则还不能把进步全归功于方法。A：继续试行，匹配词表难度；若后续仍有改善且耗时可接受，再保留为固定步骤。

**启示：** 一轮检查可以得出“还不能确定”。承认比较不公平，比凭一次上升就宣布成功更有助于改进。

### 工作产品：减少重复咨询

**场景：** 产品支持团队发现，用户提交工单后经常追问处理进度，准备增加自动状态通知。

**分析：** 通知可能降低追问，也可能让用户收到过多信息。不能只统计消息发送量，需要查看追问比例及投诉情况。

**行动：** P：限定一种工单类型，记录每百张工单的进度追问数、处理周期和通知投诉数。D：小范围试行，记录哪些用户实际收到通知。C：假设追问减少，但恰好试行期工单更简单；团队按复杂度重新比较，并检查是否影响解决时间。A：证据支持时扩大试行，同时写入通知触发条件、负责人和异常处理流程。

**启示：** A 不只是“再努力”，而是把已学到的内容落实到日常流程。扩大后仍需观察。

### 误用反例：复盘表填满，问题仍重复

**场景：** 团队每周给延期项目填写 PDCA 表，C 栏写“沟通不足”，A 栏写“加强沟通”，下周再次延期。

**分析：** 原因没有证据，行动也无法判断是否执行。看似四格齐全，实际没有可检验的改变。

**行动：** 从具体问题入手，例如需求变更直到开发结束才被发现。下一轮试行“变更当日记录影响并通知负责人”，跟踪变更到确认的间隔及返工次数，而不是把会议数量当作改善结果。

**启示：** 判断是否形成循环，要看上次检查是否改变了下次行动，不看表格是否完整。
