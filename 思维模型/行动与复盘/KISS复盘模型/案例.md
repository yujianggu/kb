# KISS复盘模型：案例

> 基于通用知识整理，尚未与视频内容核对。
> 内容类型：通用知识版

**版本与边界：** 采用Keep、Improve、Stop、Start四类复盘版本。两个S的排列在资料中有差异，本稿明确顺序；它不是Keep It Simple的软件设计原则。

> 下方原有的三个情境均为假设案例，由本库整理；行动描述不是已发生的效果报告，反例用于说明边界。


## 真实案例：GitHub 把故障经验变成保留、停止与新增措施（2018 年）

### 背景与已发生的结果

2018 年 10 月 21 日，GitHub 一次网络维护引发短暂断连，随后触发数据库拓扑变化，最终服务降级持续 24 小时 11 分钟。官方复盘说明，恢复过程中优先维护数据完整性，并承认恢复时间估计没有纳入全部变量；后续计划包括限制跨区域数据库主节点提升、细化服务状态报告以及加强故障情境验证。[GitHub 官方事后分析](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/)

### 具体行动：把临时恢复与长期改变分开

GitHub 报告记录，恢复中需要处理复制滞后和积压任务，团队在优先维护数据完整性的同时，也承认状态沟通和恢复估计存在不足。长期措施涉及自动故障转移范围、状态报告及失效情境测试。这些不是同一种行动，不能都缩成一句“优化系统”。[恢复经过与后续措施](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/)

四栏整理要在原因分析之后进行：先判断哪些条件促成故障，再决定保留什么、修改什么、停止什么、增加什么。事故时临时暂停的处理不一定要永久停止；平时有效的自动化也可能只需限制适用范围。KISS 的作用是让行动性质清楚，不是让每栏必须填同样多的条目。

### 结果口径：恢复可用不等于经验已落地

服务重新正常，是恢复阶段的结果；后续改进是否完成，是另一条需要追踪的线。原报告中的承诺不能直接写成长期效果证明。团队应用时，可以把行动状态分为提出、批准、实施、验证四类，避免“已讨论”被误当成“已解决”。保留原则也应有理由，而不只记住事故中最受关注的失误。

### 与模型的对应（本库分析）

下面是本库用 KISS 进行的事后整理，官方没有采用这个标签：Keep 是保留数据完整性优先原则；Improve 是改善恢复估计和状态沟通；Stop 是停止不适合应用架构的跨区域自动提升；Start 是增加故障注入与失效情境验证。四栏把“以后注意”变为不同性质的行动。

### 可借鉴步骤

把一次项目中的事实逐条放进四栏，每条附一项证据。特别检查“保留”栏，防止一次失败导致所有做法全被推翻；“停止”栏要明确什么条件下停止，“开始”栏则明确首次执行和验收时点。每轮只选择团队有资源完成的少量行动，下次检查结果。

实际使用四栏时，还应区分立即恢复服务的临时动作与长期制度改变。临时关闭或绕过某功能，可能只适合事故期间，不能未经检查就作为永久做法保留。

### 填写示例：复盘一次课程直播

以下是本库编写的假设复盘，不是 GitHub 事件的细节。

| 栏目 | 具体行动 | 为什么这样分类 |
| --- | --- | --- |
| Keep | 保留开场前设备检查 | 检查确实提前发现过连接问题 |
| Improve | 给主持人准备明确的故障通知模板 | 现有通知太笼统，听众不知道要等多久 |
| Stop | 停止临时在多个渠道更换入口 | 多入口造成参与者分流和混乱 |
| Start | 增加一个与主平台独立的状态入口 | 主平台异常时仍能说明当前安排 |

对每一行再加负责人、完成时点和验证方式。例如“新增入口”的验收不是页面存在，而是模拟主平台不可用时，主持人仍能访问并发出清楚通知。这个测试发现新限制时，应再调整方案，而不急着在表格上打勾。

会议主持人还应防止讨论只集中在“开始做更多”。新增工作需要时间；若所有建议都增加检查而没有停止低价值活动，团队可能因负担过重绕过流程。每个新增项都说明占用多少维护资源，并优先选择能针对已知失效路径的少量措施。

复盘结束后，用一个真实的下一次活动检验“改善”和“开始”两栏，保留观察结果。若某项措施无效，允许转入停止或重新设计；四栏应随经验变化，不是一次填写后永久有效的制度清单。

### 适用限制

复盘文章中的新增措施是当时承诺，不能仅凭文章就认定后续故障已消除。四栏也不是原因分析的替代品：若没有弄清数据库与应用的关系，只填“加强沟通”仍无效。本案例可借鉴的重点是把复盘结论变成可执行、可追踪的不同动作，而不是模仿其技术配置。

## 假设练习

> 以下保留原有假设练习，供迁移和反例对照；不属于上述真实事件。

### 1. 生活学习：调整一周学习节奏（假设）

**情境：** 假设阿琳周末觉得学习很累，却不知道哪些安排该保留。

**分析：** 她查看记录发现晨间练习容易坚持，晚间整套模拟常做不完，资料收藏则占了不少时间。四类应针对这些做法，而非评价自己自律与否。

**行动：** 保留晨间练习，改进晚间任务长度，停止睡前无目的收藏，开始每周一次错因回看；先实施两项改变，其余排到之后，避免同时重排全部日程。

**观察点：** 将暂未执行的两项放入候选清单，并注明为何推迟；否则每次复盘继续增加动作，会让计划重新超载。

**启示：** 分类帮助识别已有优势，也要控制改变数量；下一周根据实际阻碍调整，不能只靠感受宣布方案有效。

### 2. 工作产品：回看需求评审（假设）

**情境：** 假设团队评审会经常超时，但提前共享图稿对开发有帮助。

**分析：** 如果笼统决定取消所有评审，可能同时丢掉有效交流。应拆开准备、讨论和记录三个环节。

**行动：** 保留提前发图，改进议题筛选，停止会上逐字朗读文档，开始记录未决问题及负责人。试行两次后查看是否仍遗漏关键决策，并确认异步阅读负担。

**观察点：** 如果会后反复补开小会，要把这部分时间一起计算，防止主会议缩短却让整体协作成本上升。

**启示：** 停止低价值环节与保护有效做法可以同时进行；缩短会议本身并非唯一成功标准。

### 3. 误用反例：投票决定删测试（假设）

**情境：** 假设大多数人觉得发布测试耗时，在Stop栏投票删除所有检查。

**分析：** 投票表达了负担感，却没有证明检查没有价值；少发生事故可能正与它发挥作用有关。

**行动：** 先查哪些检查重复、哪些能发现真实风险，针对一个冗余步骤试验简化，保留必要质量要求并观察漏检情况。

**观察点：** 反对删除的人应能说明风险证据，支持删除的人也可提出等效替代办法；讨论应聚焦功能，而非谁更保守。

**启示：** KISS选择的是改进方向，不是免除证据责任。删步骤前先识别它的功能，避免用效率口号移走保护措施。
