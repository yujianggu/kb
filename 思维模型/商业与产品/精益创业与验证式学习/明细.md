# 精益创业与验证式学习｜明细

假设一个团队收到十条“这个工具很有用”的评价，随后投入两个月开发。缺少的环节是：评价是否来自目标客户，他们是否遇到过这个问题，是否愿意付出钱或改变流程，以及团队能否按承诺交付。精益创业用实验把这些问题拆开，使投入随着证据推进。

核心概念参考[Eric Ries的官方方法说明](https://theleanstartup.com/principles)；下列执行步骤、证据表与检查规则为本库整理，未宣称是原作者规定的统一标准。

## 1. 验证式学习在验证什么

学习结果应能写成：“原来我们认为X；在条件C下观察到E；因此将判断改为Y；下一步做Z。”只写“收获很大”无法让别人复查。

一份完整商业设想包含多条假设，应逐项验证：

| 假设 | 可观察的问题 | 常见错误替代 |
|---|---|---|
| 问题存在 | 最近何时发生？现有处理方式花了什么代价？ | 社交媒体热度 |
| 目标客户匹配 | 谁实际使用、谁付款、谁有批准权？ | 访谈对象都说有兴趣 |
| 价值成立 | 在明确任务中，结果是否比原做法更有用？ | 演示看起来新颖 |
| 购买成立 | 面对真实价格和交付条件是否实际付款？ | 问卷里选择“愿意付费” |
| 交付成立 | 在承诺时间与质量下能否完成？返工多少？ | 创始人通宵完成一次 |
| 经济成立 | 计入人工、退款和获客后是否仍值得继续？ | 有营业收入 |
| 持续使用成立 | 下一个自然使用周期是否再次使用或购买？ | 一次登录或一次成交 |
| 获客可重复 | 新批次目标客户能否以可承担成本获得？ | 熟人转介绍的首批订单 |

不必等所有问题都确定才行动，但每次加大投入前应知道还有哪些关键假设未被检验。

## 2. 四个核心概念如何配合

**构建—测量—学习**是执行循环。规划时先确定要作出的决定，再问需要什么观察，最后设计最小测试。这里的倒推顺序是实践建议，避免从“想做什么功能”开始。

**MVP**服务于特定学习目标。若问题是客户能否理解价值，可以先测试清晰的演示；若问题是能否交付，必须让客户完成真实任务；若问题是能否规模化运营，纯人工试点就不足以回答。最小不等于低质量，粗糙体验可能掩盖真实价值。

**创新核算**关注能说明进展的指标。本文建议先记录基线，再查看可比较条件下的变化；功能数和总访问量可以辅助运营，但不能单独证明购买或留存假设。它也不替代财务会计。

**继续或转向**是学习后的选择。继续表示证据足以支持下一步投入；转向表示改变关键商业假设并重新测试。停掉某项假设、暂停等待条件或终止方向也是可接受的本地管理决策，不能为了保持“迭代”而无限试验。

## 3. 一轮实验的七个步骤（本库建议）

1. **写明决定。** 例如“是否投入两周开发自助版本”，避免目标仅为“再做点调研”。
2. **选关键风险。** 优先处理一旦不成立就会改变投入决定、且当前证据薄弱的假设；结合验证成本和前置条件排序，不强行给出精确总分。
3. **将假设改为可观察陈述。** 写明客户、情境、报价或条件、行为、期限。例如“符合条件的客户看到真实报价后会付款并完成试用”。
4. **预设实验设计。** 指定样本从哪里来、什么人算符合条件、测试方式、时间或预算上限、指标分母及继续／停止条件。门槛应依据业务约束制定。
5. **完成足以产生证据的测试。** 按真实能力说明交付，记录人工辅助、优惠、故障和偏离原计划的情况。
6. **解释结果。** 先核对实验是否按计划执行，再判断假设受到支持、反驳还是结果含混。明确替代解释。
7. **记录决定。** 说明继续、转向、补证或停止的原因、剩余风险及下一轮投入上限；不在看到结果后悄悄降低门槛。

步骤3—4借鉴Strategyzer[实验卡](https://www.strategyzer.com/library/validate-your-ideas-with-the-test-card)的四个问题：假设、测试方法、测量对象和成功门槛；其他字段是为可追溯执行增加的本库约定。

## 4. 证据必须与问题匹配

| 方法 | 主要能支持什么 | 仍不能说明什么 |
|---|---|---|
| 桌面研究与外部案例 | 发现问题线索、现有替代与可能的商业结构 | 本团队能复制案例结果 |
| 具体经历访谈 | 被访者的流程、过去行为和限制 | 面对真实报价一定购买 |
| 页面、演示、预约测试 | 信息理解、响应和进一步接触意愿 | 实际交付效果或付费留存 |
| 明确报价的付费试点 | 特定客户在特定条件下愿意购买 | 无优惠时同样购买、可规模化盈利 |
| 人工辅助交付 | 核心结果能否实现、哪些步骤困难 | 无人辅助产品的完成率与成本 |
| 跨周期使用观察 | 对应批次在观察期内的回访、复购或使用 | 超出观察期的长期留存 |

证据没有脱离问题的统一排名。一次付款对购买行为很有价值，对算法精度几乎没有直接证明力；访谈对理解采购流程可能比点击率更有用。

## 5. 指标与统计边界

记录完整漏斗：接触人数／机构数、符合条件数、实际看到报价数、付款数、完成交付数、达到复购观察期的数量。每个转化率写明分子、分母、时间与计数单位，同一机构多人响应不要随意计成多个客户。

按进入时间、渠道、客户类型和报价条件区分批次。累计注册数增长可能只是投放增加；若把新老用户混在一起，也会误读留存变化。使用频率应匹配场景，年度报税工具不应以每日活跃判断价值。

本库建议区分两类门槛：

- **经营门槛**：达到某结果才值得继续投入，是团队事前选择的决策规则。
- **统计推断条件**：若要估计总体效果或主张因果关系，需要另行设计抽样、比较、样本量和不确定性分析。

小样本过线不能自动获得统计显著性；前后对比也可能受渠道、季节或客户差异影响。样本太少、报价未送达或执行失败，应记录为证据不足，不能直接断言市场不存在。不要反复查看结果直到碰巧过线再停止并宣称已验证。

## 6. 将交付和经济一起观察

记录实收口径、退款、工具消耗、直接人工时间、支付费用与返工。人工代办的学习价值可能很高，但不能把创始人免费劳动当作产品未来的零成本。

可用“收入减对应交付变动成本”观察单笔贡献，另列获客投入和固定开发成本；单笔贡献为正仍不等于净利润为正。没有跨周期数据时，不用假定长期留存推导确定的客户终身价值。具体算例见[案例](案例.md)。

## 7. 继续、转向、补证和停止

| 观察 | 可能的决定 | 下一步重点 |
|---|---|---|
| 达到事前门槛，执行有效 | 继续下一阶段 | 测试尚未覆盖的风险，不宣布全面成功 |
| 有需求与付款，但交付成本过高 | 修改交付或价格假设 | 重新测量成本及新报价下的购买 |
| 同一问题集中出现在另一类客户 | 转向该客户群的假设 | 另设样本与实验，不能挪用原转化率 |
| 样本不足或执行明显偏离 | 补证或暂停 | 先修复测试条件，保持原结果记录 |
| 关键假设反复受反证，且无可承担的替代路径 | 停止 | 保存证据，避免因沉没成本继续投入 |

以上是决策提示，不是自动裁决规则。每轮应有时间、资源边界；变更门槛或样本定义时创建新版本并解释原因。

## 8. 适用边界与常见误用

适用于关键不确定性可以分解、能以有限代价观察真实行为的创新任务。对于安全关键、强监管、硬件或基础设施项目，可先验证需求和流程，但工程可靠性与专业验收仍须独立完成；不能用“MVP”降低必要的交付底线。

常见误用包括：先开发再补假设；只采访朋友；只记录支持意见；把未付款预约写成订单；把高强度人工服务结果外推为自动化表现；一次失败立刻换方向；只保留成功实验。这些做法都会削弱学习的可复查性。

## 9. 与资料组织的连接

将当前商业假设保存在创意主档案，将原始依据保存在来源记录，将实验设计及实际结果保存在独立实验记录，将由此产生的投入决定保存在比较或复审意见中。使用稳定创意ID和实验ID连接它们；同一实验的新结果更新原记录，实质改变测试条件则另建版本或实验。

这种资料组织是本库实践建议，精益创业本身不规定文件夹名称。Git能记录文字变化，却不能补足没有记录的样本条件或决策理由。
