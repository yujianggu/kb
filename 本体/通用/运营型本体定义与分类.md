# 运营型本体：定义、特征与分类

## 一、什么是运营型本体

“运营型本体”不是一个全球统一的标准术语，而是一种强调业务运行和决策执行的本体类型。

普通本体主要回答：

```text
业务中有哪些对象？
对象有什么属性？
对象之间有什么关系？
```

运营型本体进一步回答：

```text
对象当前处于什么状态？
可以基于哪些规则进行判断？
谁可以执行什么动作？
动作执行后会改变哪些业务状态？
结果如何写回系统并形成反馈？
```

因此可以概括为：

```text
运营型本体
= 语义对象
+ 实时状态
+ 业务逻辑
+ 可执行行动
+ 权限与治理
+ 反馈闭环
```

Palantir 官方将 Ontology 描述为组织的运营层。它不仅包含对象、属性和链接等语义元素，还包含 Action、Function 和动态安全等动力元素。[Palantir Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview)

## 二、普通本体与运营型本体的区别

| 对比项 | 普通本体 | 运营型本体 |
|---|---|---|
| 核心目的 | 统一概念和语义 | 支持真实业务运行和决策 |
| 主要内容 | 概念、属性、关系、约束 | 对象、状态、逻辑、动作、权限、反馈 |
| 典型问题 | 订单是什么？ | 这个订单现在该怎么处理？ |
| 数据使用 | 主要用于查询和理解 | 用于实时判断和业务操作 |
| 业务动作 | 通常由外部系统处理 | 本体内定义或关联业务动作 |
| 安全 | 可能由外部系统提供 | 绑定到对象、属性、函数和动作 |
| 输出 | 知识、查询结果、推理结论 | 批准、冻结、分配、调度、召回等行动 |
| 反馈 | 不一定形成闭环 | 行动结果回流，改进规则和模型 |

### 例子：订单分配

普通本体：

```text
订单 ──分配到──▶ 仓库
```

运营型本体：

```text
订单状态 = 供应风险
目标仓库库存充足
当前用户 = 供应链主管
运输能力 = 可用
        ↓
允许执行“重新分配订单”
        ↓
更新订单、通知仓库、同步物流系统、记录审计
```

## 三、运营型本体的核心构成

### 1. 业务对象

```text
订单、车辆、零件、供应商、库存、设备、质量问题
```

### 2. 状态

```text
订单：待处理、风险中、已分配、已发运
车辆：生产中、待检、已放行、召回中
质量问题：新建、分析中、整改中、已关闭
```

### 3. 业务逻辑

```text
库存不足的仓库不能分配紧急订单
质量门未通过的车辆不能放行
严重安全问题不能自动关闭
```

### 4. 业务行动

```text
重新分配订单
冻结零件批次
批准车辆放行
创建整改任务
启动服务活动
发起召回
```

### 5. 权限与治理

```text
谁可以查看？
谁可以修改？
谁可以批准？
谁可以执行高风险动作？
AI 可以调用哪些函数和行动？
```

### 6. 反馈闭环

```text
行动执行
  → 业务结果
  → 用户反馈
  → 问题分析
  → 规则或模型改进
```

Palantir 官方强调，Ontology 将数据、逻辑、行动和安全结合起来，用于支持人类和 AI Agent 的决策与协作。[The Ontology system](https://www.palantir.com/docs/foundry/architecture-center/ontology-system)

## 四、按抽象层次分类

### 1. 上层本体（Upper Ontology）

描述所有领域都可能共享的基础概念：

```text
实体、对象、事件、时间、地点、过程、角色、状态
```

### 2. 核心本体（Core Ontology）

描述一个组织或多个业务领域共享的通用概念：

```text
客户、供应商、产品、订单、组织、人员、地点、合同
```

### 3. 领域本体（Domain Ontology）

描述特定行业或专业领域：

```text
汽车：车辆、零件、VIN、电池包、召回
医疗：患者、诊断、药物、病床、手术
金融：账户、交易、客户、风险、合规事件
制造：设备、工位、工艺、批次、质量门
```

### 4. 任务本体（Task Ontology）

描述一个任务或业务活动中的概念：

```text
问题分析、风险评估、供应商审核、召回评估、订单审批
```

### 5. 应用本体（Application Ontology）

面向具体应用或系统：

```text
质量问题管理系统中的问题、工单、责任人、审批和整改
```

## 五、按业务作用分类

### 1. 描述型本体

用于描述领域中的对象和关系：

```text
车辆属于车型
车辆安装电池
电池包来自批次
批次由供应商提供
```

重点是“世界是什么”。

### 2. 分析型本体

用于查询、统计、推理和风险分析：

```text
哪些车辆使用了同一批次的电池？
哪些供应商的缺陷率正在上升？
某个问题可能影响哪些产品？
```

重点是“从事实中得到什么结论”。

### 3. 运营型本体

用于执行决策和改变业务状态：

```text
冻结批次
重新分配订单
批准放行
创建整改任务
启动召回
```

重点是“接下来要做什么”。

三类能力通常可以形成一条链：

```text
描述型 → 分析型 → 运营型
```

## 六、按形式化程度分类

### 1. 词汇型本体

只规定术语和基本定义：

```text
订单、客户、仓库、库存
```

### 2. 分类型本体

进一步规定层级：

```text
车辆
├── 乘用车
├── 商用车
└── 特种车辆
```

### 3. 关系型本体

增加对象之间的关系：

```text
客户提交订单
订单包含产品
仓库存储产品
```

### 4. 逻辑型本体

增加约束和推理：

```text
如果车辆使用高压电池，则必须有电池安全检验记录
```

### 5. 运营型本体

再增加状态、行动、权限、审批和写回：

```text
如果电池批次风险等级为高，
则冻结该批次并生成影响车辆清单；
只有质量负责人批准后才能解除冻结。
```

## 七、当前 TQM 模型属于哪一类

TQM / LI-TQM 模型不是单纯的概念本体，而是一个组合模型：

```text
领域本体：
  质量问题、质量门、供应商、车辆、零件、批次

任务本体：
  问题分析、根因分析、整改、验证、召回评估

分析型本体：
  风险评分、问题聚类、影响范围分析、质量指标

运营型本体：
  冻结批次、质量门放行、创建工单、启动整改、关闭问题

应用本体：
  PQCP、QWO、AQMS、SQM、MES 等系统中的具体业务对象
```

因此，它可以称为：

> 面向汽车质量管理的领域运营型本体。

## 八、如何判断一个本体是否是运营型

- 是否有实时业务对象？
- 是否有明确的对象状态？
- 是否定义业务规则？
- 是否定义可执行动作？
- 是否有动作提交条件？
- 是否区分查看、编辑、批准和执行权限？
- 是否能写回订单、库存、生产或售后系统？
- 是否记录操作人、时间、原因和结果？
- 是否能把结果反馈给下一轮决策？

如果只能回答“有什么对象、对象之间是什么关系”，它更接近描述型本体；如果还能回答“现在发生了什么、应该采取什么措施、谁可以批准、执行后如何改变系统状态”，它就接近运营型本体。

## 九、最终总结

“运营型本体”不是本体论的唯一分类，而是强调面向业务运行和决策执行的一种本体形态。

最实用的分类方式是：

```text
按抽象层次：
上层本体 → 核心本体 → 领域本体 → 任务本体 → 应用本体

按业务作用：
描述型本体 → 分析型本体 → 运营型本体

按形式化程度：
词汇型 → 分类型 → 关系型 → 逻辑型 → 运营型
```

在 Palantir 语境中，运营型本体的核心可以概括为：

```text
业务对象 + 实时状态 + 业务逻辑 + 可执行行动 + 动态安全 + 结果反馈
```

它的目标不是单纯建立一个知识库，而是让人、应用和 AI Agent 能够在同一个业务世界中理解、判断并安全地采取行动。
