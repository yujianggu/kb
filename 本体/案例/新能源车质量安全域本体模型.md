# 新能源车实物供应链：质量安全域本体模型

## 0. 文档定位

本文以一家类似理想汽车的新能源车制造企业为示例，设计“实物供应链体系”中的质量安全域本体模型。

这里的企业名称只用于说明业务场景，不代表理想汽车公开披露的内部系统、数据结构或管理流程。

模型目标是把以下五个质量域连接起来：

```text
供应链质量 → 零件质量 → 制造质量 → 设计质量 → 售后质量
```

它们不是五套孤立的台账，而是一条可追溯的质量安全链：

```text
设计要求
  ↓
供应商与来料
  ↓
零件制造与检验
  ↓
整车装配与测试
  ↓
交付与使用
  ↓
售后故障与现场反馈
  ↓
设计、供应商和制造过程改进
```

## 1. 一分钟理解模型

质量安全域本体要回答的不是“某张表里有多少不良品”，而是：

- 哪一台车使用了哪一批电池、哪一个零件？
- 这些零件来自哪家供应商、哪条产线、哪一台设备？
- 它们是否满足设计要求和法规要求？
- 某个缺陷影响了哪些车辆、订单和客户？
- 应该采取隔离、返工、召回、软件修复还是设计变更？
- 谁可以批准放行、停线或召回？

核心模型可以表示为：

```text
质量安全决策 = 实物对象 + 质量事实 + 风险逻辑 + 控制行动 + 权限审计
```

## 2. 建模范围与边界

### 2.1 覆盖范围

本文覆盖新能源车实物供应链中的：

1. 供应商准入、审核和绩效；
2. 原材料、零件和批次质量；
3. 来料、过程和成品检验；
4. 设计要求、变更和验证；
5. 生产缺陷、质量门和放行；
6. 车辆交付、故障、维修和客户反馈；
7. 缺陷遏制、根因分析、纠正预防和召回。

### 2.2 暂不展开的领域

财务结算、人力资源、营销线索和完整售后经营模型不在本文范围内，只保留与质量安全相关的接口。

## 3. 总体本体架构

### 3.1 五个质量子域

| 子域 | 主要关注对象 | 核心问题 |
|---|---|---|
| 供应链质量 | 供应商、工厂、合同、批次、审核 | 供应商是否稳定、可控、可追溯？ |
| 零件质量 | 零件、原材料、批次、检验、缺陷 | 来料和零件是否满足规范？ |
| 制造质量 | 车辆、工位、工艺、设备、过程参数 | 装配过程是否稳定，车辆是否可放行？ |
| 设计质量 | 需求、设计版本、规范、验证、变更 | 设计是否满足安全、法规和使用场景？ |
| 售后质量 | 客诉、故障、维修、现场车辆、服务活动 | 车辆在真实使用中是否出现系统性问题？ |

### 3.2 共享的核心对象

五个子域需要共同引用以下对象：

```text
Vehicle        整车
Part           零件
Material       原材料
Supplier       供应商
Plant          工厂
ProductionLine 生产线
Batch          批次
SerialNumber   序列号
QualityEvent   质量事件
Defect         缺陷
Risk           风险
CorrectiveAction 纠正措施
```

### 3.3 分层结构

```text
战略与治理层：质量目标、风险政策、法规义务、召回策略
                    ↓
决策与规则层：风险评分、放行规则、抽检规则、升级规则
                    ↓
质量事实层：检验结果、过程参数、故障码、客诉、审核记录
                    ↓
实物对象层：车辆、零件、材料、批次、设备、工厂、订单
                    ↓
数据来源层：ERP、PLM、MES、QMS、WMS、TMS、CRM、售后系统、IoT
```

## 4. 核心对象模型

### 4.1 Vehicle：整车

```yaml
Vehicle:
  key: vin
  properties:
    - vin
    - model
    - configuration
    - productionDate
    - plant
    - deliveryDate
    - softwareVersion
    - qualityStatus
    - customerRegion
```

`VIN` 是车辆级追溯主键。车辆应能够关联到生产批次、装配工位、关键零件序列号、软件版本、质量门结果和售后维修记录。

### 4.2 Part：零件

```yaml
Part:
  key: partNumber
  properties:
    - partNumber
    - partName
    - partCategory
    - safetyCriticality
    - revision
    - specification
    - lifecycleStatus
```

典型零件分类：

```text
动力电池包、电芯、BMS、驱动电机、逆变器
制动系统、转向系统、安全气囊、摄像头、雷达
车身结构件、座椅、线束、热管理部件
```

### 4.3 Material：原材料

例如：铝材、铜材、钢材、正负极材料、胶黏剂、塑料粒子和涂料。

原材料不应只记录名称，还要记录供应批次、成分、证书、有效期和检验状态。

### 4.4 Supplier：供应商

```yaml
Supplier:
  key: supplierId
  properties:
    - name
    - supplierLevel
    - approvedStatus
    - riskLevel
    - region
    - certificationStatus
    - qualityScore
```

供应商应进一步关联其工厂、生产线、审核、整改、供货零件和质量事件，而不是只有一个供应商名称。

### 4.5 Batch 与 SerialNumber：批次和序列号

批次用于追踪一组具有共同来源或生产条件的实物；序列号用于追踪单个零件或组件。

```text
供应商批次 SUP-BAT-20260901
    ↓
电芯批次 CELL-BAT-8842
    ↓
电池包序列号 PACK-000918
    ↓
车辆 VIN LXA123456789
```

这条链是质量召回和缺陷影响范围分析的基础。

### 4.6 Plant、Line、Workstation、Equipment

```text
Plant              工厂
ProductionLine     生产线
Workstation        工位
Equipment          设备
Tooling            工装
```

制造质量需要知道某个缺陷究竟发生在哪个工厂、哪条线、哪个工位、哪台设备和哪个班次。

### 5.1 供应链关系

```text

```

```text

VehicleModel ── conformsTo ──▶ DesignSpecification
```

### 5.3 制造关系

```text
Vehicle ── producedAt ──▶ Plant

Vehicle ── passesThrough ──▶ Workstation
Workstation ── uses ──▶ Equipment

```

### 5.4 质量关系

```text
Inspection ── inspects ──▶ Part / Vehicle / Material

Defect ── affects ──▶ Part / Vehicle / Batch
```

### 5.5 售后关系

```text

Vehicle ── receives ──▶ RepairOrder
RepairOrder ── replaces ──▶ Part
FieldFailure ── mayIndicate ──▶ SystemicDefect
```

## 6. 五个质量子域的详细模型

### 6.1 供应链质量域

供应链质量关注“供应来源是否可靠，以及风险能否在进入工厂前被发现”。

核心对象：

```text
Supplier
SupplierPlant
SupplierAudit
SupplierCertification
SupplierPerformance
SupplierCorrectiveAction
IncomingShipment
SupplierBatch
```

关键关系：

```text
Supplier ── hasAudit ──▶ SupplierAudit
Supplier ── supplies ──▶ Part
Supplier ── owns ──▶ SupplierPlant
SupplierBatch ── contains ──▶ Part
SupplierAudit ── creates ──▶ SupplierCorrectiveAction
```

关键规则：

```text
未通过准入审核的供应商不能供货
安全关键零件必须来自已批准的供应商工厂
供应商证书过期时，相关来料进入待检或冻结状态
连续批次不良率超过阈值时，自动升级供应商风险
```

关键指标：

```text
PPM 不良率
批次合格率
准时交付率
供应商整改关闭周期
重复缺陷率
高风险零件覆盖率
```

### 6.2 零件质量域

零件质量关注“一个零件是否符合设计规范，且是否能够追溯到具体来源和批次”。

核心对象：

```text
Part
PartRevision
PartSpecification
IncomingInspection
PartTestResult
PartDefect
PartBatch
CertificateOfConformance
```

关键规则：

```text
零件版本必须与车辆配置匹配
安全关键零件缺少合格证时不得入库
检验状态为 FAILED 的批次不能投产
同一批次出现严重缺陷时，自动冻结同批次库存
```

### 6.3 制造质量域

制造质量关注“生产过程是否受控，以及最终车辆是否满足放行条件”。

核心对象：

```text
ProductionOrder
VehicleBuild
Workstation
ProcessParameter
QualityGate
EndOfLineTest
Nonconformance
ReworkOrder
ReleaseDecision
```

关键关系：

```text
ProductionOrder ── builds ──▶ Vehicle
Vehicle ── passesQualityGate ──▶ QualityGate
QualityGate ── hasResult ──▶ TestResult
Nonconformance ── requires ──▶ ReworkOrder
ReleaseDecision ── releases ──▶ Vehicle
```

关键规则：

```text
关键质量门未通过，车辆不能放行
安全相关扭矩参数超限，自动暂停工位
返工完成后必须重新执行受影响的检验项目
相同工位连续出现同类缺陷时，升级为过程异常
```

### 6.4 设计质量域

设计质量关注“产品设计是否在真实使用、法规和安全约束下满足要求”。

核心对象：

```text
VehicleModel
DesignRequirement
SafetyRequirement
RegulatoryRequirement
PartSpecification
DesignRevision
EngineeringChange
DesignVerification
DesignValidation
FailureMode
RiskAnalysis
```

关键关系：

```text
SafetyRequirement ── appliesTo ──▶ VehicleModel
DesignRequirement ── verifiedBy ──▶ DesignVerification
EngineeringChange ── changes ──▶ DesignRevision
FailureMode ── mitigatedBy ──▶ DesignControl
DesignRevision ── defines ──▶ PartSpecification
```

关键规则：

```text
安全关键设计变更必须完成验证后才能生效
设计变更必须评估对库存、在制品和已交付车辆的影响
未关闭的高严重度失效模式不得进入量产放行
软件、硬件和零件版本必须与车型配置兼容
```

### 6.5 售后质量域

售后质量关注“车辆在真实使用中暴露出的质量问题，是否反映出系统性缺陷”。

核心对象：

```text
CustomerComplaint
ServiceVisit
RepairOrder
FieldFailure
DiagnosticCode
ReplacedPart
TechnicalServiceBulletin
Campaign
RecallCase
CustomerFeedback
```

关键关系：

```text
CustomerComplaint ── creates ──▶ ServiceVisit
ServiceVisit ── creates ──▶ RepairOrder
RepairOrder ── replaces ──▶ Part
FieldFailure ── linkedTo ──▶ Vehicle / Batch / SoftwareVersion
FieldFailure ── contributesTo ──▶ QualityInvestigation
QualityInvestigation ── mayCreate ──▶ RecallCase
```

关键规则：

```text
同一 VIN 和同一故障码重复出现时，创建重复维修风险
同一零件批次跨区域出现相同故障时，触发批次调查
涉及人身安全的故障必须立即升级
召回决策必须保留影响范围、依据、审批人和执行状态
```

## 7. 跨域质量事件模型

五个子域通过 `QualityEvent` 和 `Defect` 连接。

### 7.1 QualityEvent：质量事件

```yaml
QualityEvent:
  key: eventId
  properties:
    - eventType
    - severity
    - detectedAt
    - detectedBy
    - sourceSystem
    - status
    - containmentStatus
```

事件类型可以包括：

```text
来料不合格
过程参数超限
质量门失败
客户投诉
道路故障
安全事故
供应商审核不合格
法规不符合
```

### 7.2 Defect：缺陷

缺陷是对质量事件的标准化描述，可以关联：

```text
缺陷类别
故障模式
严重度
发生频度
可探测性
根因
影响零件
影响车辆
影响批次
```

### 7.3 风险评分

可建立一个用于优先级排序的风险评分：

```text
Risk Score = Severity × Occurrence × Detectability × Exposure
```

这不是固定行业公式，而是一个建模示例。企业应根据自己的质量体系、法规和安全政策定义参数及阈值。

## 8. 端到端案例：电池包潜在热失控风险

### 8.1 发现问题

售后系统在多个地区收到相似的高压电池故障码。质量工程师发现这些车辆使用了同一供应商、同一电芯批次。

本体查询路径为：

```text
FieldFailure
  → Vehicle
  → BatteryPack
  → CellBatch
  → Supplier
  → SupplierPlant
  → IncomingInspection
  → ProductionLine
```

### 8.2 风险判断

系统综合以下事实：

```text
相同故障码在多个地区重复出现
车辆使用相同电芯批次
该批次曾出现内阻检测异常
供应商近期过程能力下降
该故障可能影响高压安全
```

风险逻辑将事件升级为高优先级质量调查。

### 8.3 遏制行动

系统提供一个 `ContainBatteryBatch` 行动：

```text
输入：电芯批次、影响车辆范围、遏制原因

执行条件：
  当前用户拥有高压系统质量权限
  风险等级达到高或严重
  影响范围分析已完成

执行结果：
  冻结尚未投产的相关批次
  标记使用该批次的在制车辆
  创建售后检查任务
  通知供应商和工厂质量负责人
  触发设计与制造联合调查
```

### 8.4 纠正与验证

调查可能产生：

```text
供应商工艺整改
来料检验加严
电池包软件诊断策略更新
生产过程参数调整
设计验证补充测试
售后服务活动或召回
```

每项措施都应关联验证结果，确认缺陷是否真正关闭，而不是只记录“已处理”。

## 10. 建模实施路线

### 阶段一：建立最小可用模型

优先选择一个高价值场景，例如：

```text
关键电池批次追溯与风险遏制
```

只实现必要对象：车辆、零件、批次、供应商、质量事件和行动。

### 阶段二：补齐制造和设计连接

加入工厂、工位、设备、过程参数、设计版本和验证结果，形成从设计到生产的链路。

### 阶段三：接入售后反馈

将客户投诉、维修记录、故障码和软件版本连接到 VIN 与零件批次。

### 阶段四：引入风险模型和 AI

让 AI 在明确的对象、函数和权限边界内完成检索、归因建议、影响范围分析和行动建议。

### 阶段五：形成质量闭环

持续记录遏制、纠正、验证、放行和召回结果，为供应商评分、设计改进和制造优化提供反馈。

## 11. 质量安全域的关键原则

1. **以实物对象为中心**：围绕 VIN、零件序列号、批次和设备建立追溯，而不是只围绕系统表设计。
2. **以事件和缺陷为连接点**：把供应链、制造和售后中的质量事实统一成可分析对象。
3. **区分事实、判断和行动**：检验结果是事实，风险评分是判断，冻结批次是行动。
4. **保留版本和时间维度**：设计版本、软件版本、零件版本和有效期必须可追踪。
5. **将安全关键对象单独分级**：电池、高压、制动、转向和约束系统需要更严格的规则与权限。
6. **所有重大行动可审计**：停线、放行、遏制、返工和召回都要记录依据、审批和结果。
7. **先建闭环，再扩范围**：从一个可度量的质量决策场景开始，逐步扩展到全域。

## 12. 最终模型摘要

```text
设计质量定义“应该是什么”
供应链质量确认“由谁、在哪个来源生产”
零件质量确认“来料是否符合要求”
制造质量确认“装配过程和整车是否合格”
售后质量验证“真实使用中是否持续满足要求”

质量安全本体把这五个问题连接成：

设计要求
  → 供应商与批次
  → 零件与检验
  → 工艺与整车
  → VIN 与客户使用
  → 缺陷调查与纠正行动
  → 设计、供应链和制造改进
```

这套模型的最终目标，不是制作一张更复杂的关系图，而是让企业能够在面对质量风险时，快速回答：**影响了什么、为什么发生、谁负责、现在该做什么，以及如何证明问题已经解决。**

本章将前面的概念模型映射到汽车行业常用的质量、安全和合规框架。这里的“映射”表示建模参考关系，不表示本模型已经通过任何认证或满足某家企业的全部审核要求。

| 标准 / 方法 | 主要关注点 | 建议映射的本体对象 |
|---|---|---|
| IATF 16949 | 汽车质量管理体系、过程管理、供应商和变更控制 | QualityProcess、Supplier、Audit、ChangeRequest、CorrectiveAction、KPI |
| ISO 9001 | 质量管理、风险思维、文件化信息、持续改进 | QualityPolicy、Risk、Document、Process、ImprovementAction |
| APQP | 产品质量先期策划、阶段评审、交付物管理 | QualityPlanning、ProjectPhase、Milestone、Deliverable、Review |
| PPAP | 生产件批准、样件、过程能力和批准状态 | PartApproval、Submission、Sample、CapabilityStudy、ApprovalDecision |
| AIAG/VDA FMEA | 失效模式、原因、后果、风险和措施 | FailureMode、Cause、Effect、RiskAnalysis、Control、Action |
| MSA | 测量系统能力和测量结果可信度 | MeasurementSystem、Gauge、MSAStudy、MeasurementResult |
| SPC | 过程稳定性、控制图和过程能力 | ProcessCharacteristic、ControlChart、OutOfControlEvent、CapabilityIndex |
| ISO 26262 | 道路车辆功能安全和安全生命周期 | SafetyGoal、Hazard、ASIL、SafetyRequirement、SafetyCase、Verification |
| ISO 21448 | 预期功能安全、场景和性能局限 | Scenario、OperationalLimitation、SOTIFHazard、ValidationResult |
| ISO/SAE 21434 | 汽车网络安全风险和生命周期管理 | CybersecurityGoal、Threat、Vulnerability、TARA、SecurityControl |
| UNECE R155/R156 | 网络安全管理和软件更新管理 | CybersecurityManagement、SoftwareUpdate、Campaign、ComplianceEvidence |
| 产品安全与召回法规 | 缺陷判定、影响范围、通知、召回和关闭 | SafetyDefect、AffectedVehicle、RecallCase、RecallAction、ClosureEvidence |

### 13.2 质量标准证据对象

为了让模型可用于审核和治理，不能只保存“合格 / 不合格”，还应保存形成结论的证据：

```yaml
ComplianceEvidence:
  key: evidenceId
  properties:
    - evidenceType
    - standardReference
    - documentVersion
    - createdAt
    - createdBy
    - approvalStatus
    - validityPeriod
    - storageLocation
    - hashOrFingerprint
```

典型证据包括：

```text
供应商审核报告
PPAP 提交包
过程能力研究
MSA 研究报告
FMEA 评审记录
设计验证报告
功能安全分析
网络安全风险分析
质量门放行记录
8D / CAPA 整改报告
召回影响范围分析
```

### 13.3 角色和责任对象

标准落地通常要求明确责任人，因此建议将组织角色建模，而不是只在文档中写部门名称：

```text
QualityEngineer        质量工程师
SupplierQualityEngineer 供应商质量工程师
DesignOwner             设计负责人
ManufacturingOwner      制造负责人
FunctionalSafetyOwner   功能安全负责人
CybersecurityOwner      网络安全负责人
RecallCommittee         召回评审委员会
Approver                审批人
```

关键关系：

```text
Role ── responsibleFor ──▶ QualityProcess
Person ── holds ──────────▶ Role
Person ── approves ───────▶ ApprovalDecision
Evidence ── reviewedBy ───▶ Person
```

### 13.4 标准化行动模型

将标准要求转化为可执行行动：

```text
ApproveSupplier
ReleasePartBatch
BlockMaterialBatch
OpenQualityInvestigation
ApproveEngineeringChange
StartContainment
CloseCorrectiveAction
ReleaseVehicle
LaunchServiceCampaign
InitiateRecall
```

每个行动至少应包含：

```text
输入对象
执行角色
提交条件
需要的证据
变更对象
审批链
外部系统副作用
关闭条件
审计记录
```

例如 `ReleaseVehicle` 的提交条件可以是：

```text
所有安全关键质量门已通过
无未关闭的严重不符合项
关键零件批次状态为 RELEASED
软件和硬件版本匹配车型配置
放行负责人已批准
```

## 14. 从概念模型到合规模型的差距

当前文档已经覆盖对象、关系、追溯、风险、行动和闭环，但要用于企业实际质量体系，还需要补齐：

| 差距 | 需要补充的内容 |
|---|---|
| 标准条款 | 条款编号、适用范围、解释和证据要求 |
| 企业流程 | 实际流程节点、输入、输出、责任部门和例外路径 |
| 数据映射 | ERP、PLM、MES、QMS、售后系统的字段和接口 |
| 版本管理 | 车型、零件、软件、工艺、规范和 FMEA 版本 |
| 责任体系 | RACI、审批链、替代责任人和升级路径 |
| 审核证据 | 文件、签名、时间戳、版本、附件和不可抵赖记录 |
| 法规差异 | 中国、欧洲、北美等市场的适用法规和召回要求 |
| 安全边界 | 功能安全、预期功能安全、网络安全和产品质量的边界 |
| 数据质量 | 主键、批次完整性、重复记录、缺失值和时效性 |

因此，本体模型应被视为质量体系的数字化表达，而不是质量体系本身。

## 15. 推荐的标准化建模路线

```text
阶段 1：确定质量和安全范围
  → 明确车型、工厂、供应链、市场和法规边界

阶段 2：建立对象与追溯链
  → VIN、零件号、序列号、批次、供应商、工位、软件版本

阶段 3：映射质量流程
  → APQP、PPAP、来料、过程检验、质量门、售后和召回

阶段 4：引入风险方法
  → FMEA、SPC、MSA、功能安全、SOTIF、网络安全

阶段 5：定义证据与责任
  → 记录、版本、审批人、有效期、审计和关闭条件

阶段 6：定义可执行行动
  → 放行、冻结、遏制、整改、返工、召回和验证

阶段 7：进行场景验证与审核试运行
  → 用真实缺陷、批次追溯和召回演练验证模型
```

### 15.1 最小可用标准化范围

如果不希望一开始就覆盖全部标准，建议先实现一个可验证的最小闭环：

```text
关键电池零件批次追溯
  + 来料检验
  + FMEA 风险记录
  + 过程质量门
  + 售后故障关联
  + 批次遏制行动
  + 影响车辆清单
  + 审批与证据记录
```

完成这一闭环后，再扩展到供应商 PPAP、设计变更、软件更新和正式召回流程。

## 16. 使用边界

本模型可以作为：

- 质量数据平台的领域模型；
- Palantir Ontology 的对象和行动设计蓝图；
- QMS、PLM、MES 和售后系统的整合参考；
- 质量风险和召回影响范围分析的基础；
- AI Agent 质量助手的工具与权限边界。

本模型不能直接替代：

- 企业质量手册；
- 法规符合性评估；
- 功能安全或网络安全安全论证；
- 认证审核所需的程序和记录；
- 具体车型的工程规范和测试方案。
