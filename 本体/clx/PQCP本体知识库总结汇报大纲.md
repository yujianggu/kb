# PQCP 本体知识库总结汇报大纲

> 基于项目：`/Users/yuwujian/project/ai-project/factory-pqcp`
>
> 汇报对象：业务负责人、产品负责人、架构与研发团队
>
> 汇报目标：说明 PQCP 本体知识库解决了什么问题、已经沉淀了哪些业务语义、如何支撑研发与 AI，以及下一步如何演进。

## 一、汇报结论先行

### 1.1 一句话结论

PQCP 本体知识库已经从“分散的代码、数据库表和需求文档”抽象出一套可检索、可校验、可追溯的质量问题管理业务语义模型，为统一问题对象、关系、流程、权限、导出和 AI 辅助开发提供了基础。

### 1.2 当前价值

- 统一问题（Issue）的业务身份、分类、生命周期和跨模块关系。
- 统一设计类问题、实车类问题、零件、车辆、评论、流程任务和导出对象的语义。
- 将业务规则、动作前置条件、数据来源和实现状态一起保存，降低“文档与代码不一致”的风险。
- 为 AI 提供结构化上下文，使 AI 能够按对象、属性、链接、函数和动作理解系统，而不是只依赖自然语言描述。

### 1.3 当前边界

- 项目内 YAML 是可移植的本体定义，不是 Palantir Foundry 的官方导出格式。
- 本体知识库是系统事实、目标契约和迁移边界的知识层，不等同于数据库，也不替代 OpenSpec、代码和测试。
- 部分主题标记为 `target_contract`、`active_migration_boundary` 或 `active_implementation_pending_verification`，不能直接当作已经全部上线的能力。

## 二、项目背景与业务问题

### 2.1 PQCP 的业务范围

PQCP 面向汽车研发与质量问题管理，覆盖设计类问题、非自定义实车问题、问题车辆、问题零件、问题评论、BPM 流程、看板、导出和数据权限等场景。

### 2.2 未使用本体前的典型问题

- 同一业务概念在不同问题类型中存在重复 DTO、重复字段和不同命名。
- 数据库表、后端服务、前端页面和需求文档之间缺少统一语义索引。
- 流程状态、审批动作、权限条件和异常补偿规则分散在代码中。
- 查询、导出、评论、车辆关系和零件关系容易形成跨模块语义漂移。
- AI 只能看到局部代码或文档，难以判断对象边界、权威来源和可执行动作。

## 三、本体知识库总体架构

### 3.1 四类核心语义

| 层次 | PQCP 中的表达 | 示例 |
|---|---|---|
| Data | 对象类型、属性、链接、来源 | `Issue`、`IssuePartRelation`、`IssueVehicleRelation` |
| Logic | 函数、查询规则、校验规则、映射规则 | 问题类型路由、状态投影、导出字段求值 |
| Action | 创建、提交、审批、撤回、合并、导出等动作 | 发布问题、确认 VSE、分配 DRE、生成导出批次 |
| Security/Governance | 权限、数据范围、审计、状态约束和成熟度 | 导出权限、责任领域、动作前置条件、`knownGaps` |

### 3.2 知识库目录结构

```text
knowledge/system/
├── README.md                         # 总索引、强制查阅规则和维护规则
├── pqcp-issue-base-info/             # Issue 核心身份和公共关系入口
├── pqcp-issue-classification/        # 类型、领域、阶段、来源、等级
├── pqcp-issue-relations/             # 车辆、零件、评论公共关系
├── pqcp-design-issue-data/           # DMU、EF、WDP、CMF 等设计类数据
├── pqcp-vehicle-issue-data/          # 实车问题六步数据
├── pqcp-*-workflow/                  # 问题流程、审批和 BPM 同步
├── pqcp-issue-type-configuration/    # 类型、流程、编码、权限和发布配置
├── pqcp-issue-export/                # 导出路由与导出权限边界
├── pqcp-design-issue-board/          # 设计类问题看板和运行态卡片
├── vehicle-non-custom-issue-export/  # 实车类导出字段目录与快照
└── user-query-helper/                # 人员身份、部门和权限查询函数
```

## 四、核心对象模型

### 4.1 问题主对象

`Issue` 是跨问题类型的公共业务身份，负责承载问题 ID、问题编码、问题类型、领域、阶段、来源、等级、生命周期投影以及流程引用。

汇报重点：问题类型差异通过扩展对象和 `issueTypeCode` 表达，而不是复制一套完全独立的问题主模型。

### 4.2 分类与配置对象

- `IssueType`：问题类型。
- `IssueDomain`：问题领域。
- 阶段、来源、等级和编码规则：统一字典或配置语义。
- `IssueTypeConfiguration`：问题类型基础、流程、编码、权限、看板分发和六步法配置。
- 配置片段与发布版本：保证配置变更可审计、可回滚、可解释。

### 4.3 车辆、零件和评论关系

- `IssueVehicleRelation`：问题与车辆、车型、项目阶段、配置和颜色之间的关系快照。
- `IssuePartRelation`：问题与零件、责任人、部门、供应商、版本和专业上下文的公共关系契约。
- `IssueComment`：问题评论、回复、附件和归属关系。

关键设计：关系对象不是简单的外键表，而是带有业务类型、责任人和历史快照的业务对象。

### 4.4 设计类问题对象

覆盖 DMU、EF、WDP、CMF、可维修性等设计类问题，以及：

- `MajorProcessingBatch`
- `MajorPartProcessing`
- `DesignIssueBoard`
- `BaselineVersion`
- `VseConfirmationCard`
- `DreInspectionCard`

### 4.5 实车问题六步对象

- `ProblemCause`：问题原因。
- `ProblemMeasure`：问题措施。
- `ProblemMeasureChange`：措施变更。
- `ProblemEffectVerification`：效果验证。

形成“问题提出 → 原因分析 → 措施制定 → 措施执行 → 效果验证 → 关闭/复盘”的可追踪链路。

### 4.6 流程、同步和导出对象

- `WorkflowSyncInstance`：BPM 流程实例。
- `WorkflowTaskAssignment`：节点任务、人员、超时和分配状态。
- `VehicleIssueExportFieldDefinition`：导出字段目录。
- `VehicleIssueExportSnapshot`：导出时的数据快照。
- `VehicleIssueExportBatch`：导出批次和工作簿生成。
- `ExportPolicy`、`ExportPolicyCondition`：导出权限和责任领域条件。

## 五、关键业务价值流

### 5.1 问题生命周期价值流

```text
创建问题
  → 分类与编码
  → 关联车辆/零件/人员
  → 提交与发布
  → BPM 节点流转
  → 原因与措施处理
  → 效果验证
  → 关闭、合并或撤回
  → 查询、审计与复盘
```

### 5.2 设计类问题价值流

```text
设计问题创建
  → 专业处理批次/零件处理
  → DRE/VSE 任务
  → 基线版本与看板卡片
  → 审批动作一致性校验
  → 发布或撤回
```

### 5.3 实车问题价值流

```text
实车问题
  → 问题车辆关系
  → 问题原因
  → 问题措施
  → 措施变更
  → 效果验证
  → 关闭/挂起/作废/合并
```

### 5.4 导出价值流

```text
用户发起导出
  → 解析问题类型与字段目录
  → 求值导出权限
  → 聚合多源数据
  → 创建快照和批次
  → 生成工作簿
  → 记录审计结果
```

## 六、关键动作与治理机制

### 6.1 Action 的典型类别

- 问题创建、编辑、提交、发布、撤回、关闭。
- 问题合并、挂起、作废和恢复。
- DRE 分配、VSE 确认、流程任务同步。
- 字典值维护、问题类型配置发布。
- 导出请求、导出批次生成和权限校验。

### 6.2 动作前置条件

每个写动作应明确：

1. 当前对象状态是否允许操作。
2. 当前用户是否具备角色、责任领域和数据范围权限。
3. 关联对象是否存在且未逻辑删除。
4. 是否需要 BPM 节点或审批记录作为前置条件。
5. 是否需要对象版本号防止并发覆盖。
6. 是否需要写入审计日志、同步事件或外部系统。

### 6.3 安全与治理原则

- 数据权限和导出权限分离建模。
- 人员使用稳定身份标识，展示名称只作为快照。
- 写操作必须通过动作类型表达，禁止由页面直接拼装数据库更新。
- `active`、`target_contract`、`knownGaps` 等状态必须与实现证据一起解释。
- 历史兼容字段必须标识为兼容边界，新增功能优先使用核心模型。

## 七、知识库如何支撑研发和 AI

### 7.1 对研发的支撑

- 开发前先读取主题 `README.md` 和 `ontology.yaml`，减少重复建模。
- 通过 `sources.md` 追溯表、实体、服务、接口和需求证据。
- 通过对象、链接和动作快速定位影响范围。
- 通过知识库校验脚本发现 YAML、链接、元数据和导航问题。

### 7.2 对 AI 的支撑

AI 可以基于本体回答：

- 某个问题对象有哪些属性和关系？
- QIR、TIR-QAP、DMU、EF、WDP 的差异是什么？
- 哪个服务或数据表是某字段的权威来源？
- 某个动作需要什么前置条件和权限？
- 当前能力是已实现、目标契约还是待验证？

AI 不应仅根据本体文本直接执行数据库写入；应通过经过授权的函数或 Action，并在服务端再次校验状态、权限和数据版本。

### 7.3 推荐的 AI 调用链

```text
用户问题
  → 识别本体主题
  → 读取对象/属性/链接/规则
  → 查询权威来源
  → 生成解释或执行计划
  → 调用受治理的函数/Action
  → 返回结果并记录审计
```

## 八、当前成果与成熟度汇报

建议按“已形成、正在迁移、待验证”三类汇报，而不是笼统宣称全部完成。

### 8.1 已形成

- 系统级本体总索引和主题化目录。
- Issue、分类、车辆、零件、评论等公共对象模型。
- 设计类问题、实车问题、流程同步、导出和权限等领域模型。
- 主题级来源、状态和维护规则。

### 8.2 正在迁移或目标契约

- 非自定义实车问题工作流迁移边界。
- 设计类问题展示、导出和流程一致性目标契约。
- 部分共享零件关系字段的扩展与历史兼容。

### 8.3 待验证或存在缺口

- `active_implementation_pending_verification` 主题需要补充环境、集成和回归证据。
- `active_with_known_gaps` 主题需要显式列出已知缺口，避免把目标能力当作现状。
- 数据库物理约束、跨系统同步一致性和完整端到端动作链路仍需持续验证。

## 九、度量指标建议

### 9.1 知识资产指标

- 已登记本体主题数。
- 核心对象类型、链接、函数和动作数量。
- 具备来源证据的对象和规则比例。
- 通过知识库校验的版本比例。

### 9.2 研发效率指标

- 新需求开始前查阅本体的覆盖率。
- 重复 DTO、重复字段和重复查询逻辑减少数量。
- AI 生成代码一次评审通过率。
- 因语义不一致导致的返工缺陷数量。

### 9.3 运行治理指标

- 动作权限校验覆盖率。
- 导出审计覆盖率。
- BPM 状态与业务对象状态不一致数量。
- 数据源映射失败、同步失败和死信数量。

## 十、下一步路线图

### 阶段一：夯实核心本体

- 继续完善 `Issue`、问题类型、车辆、零件和流程的统一语义。
- 为每个核心对象补齐稳定 ID、来源、状态和生命周期。
- 统一对象、链接和 Action 的命名规范。

### 阶段二：补齐运行时治理

- 将动作前置条件、权限和审计规则结构化。
- 完善 BPM 同步、导出、审批和异常补偿的事件模型。
- 建立实例数据映射和版本管理机制。

### 阶段三：接入 AI Agent

- 建立只读查询函数和受治理的写 Action。
- 为 AI 提供主题路由、对象检索、来源引用和状态解释能力。
- 引入人工审批、幂等、回滚和审计，形成可控的人机协作闭环。

### 阶段四：形成质量数据运营闭环

```text
问题数据沉淀
  → 跨车辆/零件/供应商/阶段关联
  → 风险识别与趋势分析
  → 措施推荐
  → 人工审批与业务执行
  → 效果验证
  → 反哺规则和本体
```

## 十一、汇报结束页：需要管理层决策的事项

1. 是否将 PQCP 本体知识库确定为跨模块业务语义的统一入口。
2. 是否明确核心对象、字段、动作和来源的责任人。
3. 是否为目标契约、迁移边界和待验证项建立治理流程。
4. 是否优先选择一个闭环场景接入 AI，例如问题查询、质量问题导出或措施推荐。
5. 是否建立本体版本、实例映射、审计和变更评审机制。
